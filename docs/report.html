AudioOverlay — Android 系统级视频音频工具箱

实时人声/伴奏分离 + 原声静音 — 技术调研与方案对比报告
📋 报告类型：技术调研对比 🔧 核心链路：AudioPlaybackCapture → MDX-Net → OLA → AudioTrack 📱 验证设备：canoe(SM8850) + Redmi(SM8550) 🎯 定位：个人学习非商用

1项目概述

1.1 项目目标

本项目旨在构建一个 Android 系统级视频音频工具箱，面向个人学习与非商用场景，核心能力包括：

  • 实时人声/伴奏分离：对第三方视频 App 的播放音频进行实时神经源分离（MDX-Net），输出人声或伴奏轨道。
  • 原声静音：在播放分离后音频的同时，将原始目标 App 的音频按 session 粒度静音，实现"用户只听到处理后声音"的闭环体验。
核心目标：BGM 音量降低（而非完全分离）

本项目的核心目标是降低视频中的 BGM（背景音乐）音量，使人声/台词更清晰，而非完全消除伴奏。MDX-Net 分离出人声轨（vocals）和伴奏轨（accomp）后，通过增益混合公式 output = vocals + bgmGain × accomp 实现 BGM 音量可控降低：bgmGain=0 为纯人声（BGM 完全消除），bgmGain=1 为原声（BGM 不衰减），用户可在 0~1 之间自由调节，在"听清人声"和"保留音乐氛围"之间取得平衡。

1.2 应用场景与动机

传统的音频分离工具（如 UVR、Spleeter 桌面版）均为"离线文件处理"模式——用户需先下载视频文件，再在 PC 上运行分离算法，最后手动导入结果。这种模式存在三个根本性局限：无法处理流式内容（直播、在线视频）、操作链路长（下载→分离→回放）、无法与原始播放同步（分离后的音频与视频画面存在不可控延迟）。

系统级音频分离的核心动机是将分离能力"嵌入播放链路"，在音频到达扬声器之前完成实时处理，从而支持以下场景：

K 歌 / 跟唱

实时提取伴奏轨道，用户跟随视频画面跟唱。系统级方案无需下载 MV 文件，任意视频 App 均可作为音源，原声被静音后用户只听到伴奏和自己的声音。

配音 / 台词学习

提取人声轨道用于配音练习，或提取伴奏用于影视配音。实时分离允许用户在任意片段暂停、重复，配合画面进行台词模仿。

伴奏提取 / 乐器学习

从任意在线音乐视频中实时提取伴奏，供乐器演奏者跟练。系统级捕获不依赖 App 是否提供"伴奏模式"，覆盖所有音源。

语音增强 / 听感优化

在嘈杂背景的视频中增强人声清晰度，或反之去除人声保留环境声。实时处理使得听感优化可以随播放即时生效。

BGM 降低的典型使用场景
  • 看视频时 BGM 太盖过人声/台词：许多视频（尤其是自媒体、纪录片、影视剪辑）的背景音乐音量过大，盖过了人声说话内容，调节 BGM 增益可在保留音乐氛围的同时让人声更清晰
  • 外语学习/听力训练：观看外语视频时，降低 BGM 可减少听觉干扰，更专注于人声发音和语调，提升听力训练效果
  • 播客/访谈类视频：背景音乐仅作为氛围铺垫，降低 BGM 可提升对话的可懂度（intelligibility）
  • 安静环境观看：夜间或安静环境中，BGM 可能过于突兀，降低 BGM 音量可在不静音的前提下舒适观看
为什么必须是"系统级"？ Android 的音频架构决定了普通 App 只能处理自己输出的音频。要捕获第三方 App 的播放音频，必须通过 AudioPlaybackCapture（基于 MediaProjection 权限）在系统层面拦截混音后的 PCM 流。这是唯一不需要 root 就能获取其他 App 音频的合法途径，也是本项目"系统级"定位的技术基础。

1.3 传统 DSP 方案调研

在引入神经网络分离方案之前，传统数字信号处理（DSP）领域已有多种人声/伴奏分离方法。这些方法基于信号的统计特性或物理模型，无需训练数据，计算量极低。虽然分离质量有限，但作为 baseline 对比方案和极端低延迟场景的备选，仍有调研价值。以下对五种典型传统 DSP 方案逐一分析。

(L-R)*2 / 中置声道提取（Mid-Side Processing）

原理：立体声录音中，人声通常以中置（center）方式录制——左右声道的人声信号高度相关（L≈R）；而伴奏乐器多通过声像（pan）摆位到左右两侧，左右声道差异较大。基于这一特性，可将立体声分解为 Mid（中置）和 Side（侧边）两个分量：

Mid  = (L + R) / 2    // 中置分量，含人声为主
Side = (L - R) / 2    // 侧边分量，含伴奏为主

重建公式：
L = Mid + Side
R = Mid - Side

降低 BGM（衰减 Side 分量）：
output_L = Mid + (1 - k) × Side = (L+R)/2 + (1-k)(L-R)/2
output_R = Mid - (1 - k) × Side = (L+R)/2 - (1-k)(L-R)/2

其中 k ∈ [0,1] 为 BGM 衰减系数：
  k=0 → output = 原立体声（Side 不衰减）
  k=1 → output = (L+R)/2 单声道中置（Side 完全消除，仅保留人声）

"(L-R)*2" 的含义：部分实现中 Side 直接取 L-R（不除以 2），此时重建需乘以 2 补偿：L = (2×Mid + Side)/2。两种表示等价，仅差常数增益。

  • 优点：零延迟、零计算量（仅加减运算）、无需模型、实时性完美、可在任意设备上运行
  • 缺点：仅对严格中置人声有效；人声混响（reverb）通常为立体声展宽，会被误删；BGM 中的中置乐器（如 bass、底鼓、中央钢琴）也会被保留为人声；对现代宽立体声混音（wide stereo mix）效果差；无法分离同时存在于中置的人声和乐器
本项目评估 作为零延迟 baseline 对比方案，实现极其简单（几行代码）。在人声严格中置且伴奏宽立体声的素材上可取得一定效果，但对大多数现代音乐和视频混音质量不足。本项目不采用，但可作为降级方案在无 NPU 设备上提供基础 BGM 降低功能。

EQ 频段衰减

原理：BGM 在某些频段占主导——低频段（20-200Hz）主要是 bass 和底鼓，中高频段（2-8kHz）主要是镲片、吉他泛音等。使用参数均衡器（Parametric EQ）衰减对应频段，可在一定程度上降低 BGM 音量。

  • 优点：简单、低延迟、计算量小、Android Equalizer 音频效果器原生支持
  • 缺点：人声和 BGM 频段严重重叠——人声基频范围 85-255Hz（男）/ 165-255Hz（女），泛音延伸至 8kHz 以上，与 BGM 频段完全重叠；衰减 BGM 频段必然伤人声；无法分离同一频率上同时存在的人声和乐器；仅能做粗略的频段平衡，无法实现精确分离

谱减法（Spectral Subtraction）

原理：从静音段或纯 BGM 段估计噪声（BGM）的平均功率谱，从混合信号的功率谱中减去估计的噪声谱，再通过逆变换得到增强后的人声：

|Y(ω)|² = |X(ω)|² - α·|N(ω)|²   (α 为过减因子)
人声谱幅度 = max(|Y(ω)|, β·|X(ω)|)  (β 为谱下限，防止负值)
  • 优点：经典降噪方法，原理直观，计算量适中
  • 缺点：需要纯 BGM 参考段来估计噪声谱（视频中通常没有纯 BGM 段）；BGM 是非平稳信号（随时间变化），平均谱估计不准确；减法在频谱谷值处产生"音乐噪声"（musical noise）——孤立的、随时间闪烁的频谱点，听感为"水声"或"金属声"；对人声和 BGM 频谱重叠的区域无法分离

自适应滤波 / Wiener 滤波

原理：维纳滤波（Wiener Filter）是最小均方误差（MMSE）意义下的最优线性滤波器。若有 BGM 的参考信号 n(t)，可设计维纳滤波器 H(ω) 从混合信号 x(t)=s(t)+n(t) 中估计人声 s(t)：

H(ω) = P_s(ω) / (P_s(ω) + P_n(ω))
其中 P_s 为人声功率谱，P_n 为 BGM 功率谱
人声估计: ŝ(t) = IFFT[ H(ω) · X(ω) ]
  • 优点：理论最优（MMSE），无音乐噪声伪影（相比谱减法）
  • 缺点：需要 BGM 参考信号或 BGM 功率谱估计——视频中人声和 BGM 同时存在，无法获取纯 BGM 参考；自适应滤波（如 LMS/NLMS）需要参考输入与噪声相关，在本场景中不适用；计算复杂度高于谱减法；功率谱估计的准确性直接决定分离质量

RobustPCA / NMF（非负矩阵分解）

原理：将频谱幅度矩阵分解为低秩分量（BGM，重复性强、结构稳定）和稀疏分量（人声，瞬态多、时变快）：

|X| = L + S
L: 低秩矩阵（BGM，伴奏的重复性使其频谱在时间上高度相关 → 低秩）
S: 稀疏矩阵（人声，语音的瞬态和时变特性使其频谱稀疏）
通过 PCP（Principal Component Pursuit）或 RPCA 算法求解：
min ||L||_* + λ||S||_1  s.t. |X| = L + S

NMF（Non-negative Matrix Factorization）则将频谱分解为基矩阵 W 和激活矩阵 H：|X| ≈ W × H，通过聚类将基向量分为人声基和伴奏基。

  • 优点：无监督、无需训练数据、无需参考信号；理论上可分离人声和伴奏
  • 缺点：计算量大——每帧需迭代优化（RPCA 的 SVD 分解或 NMF 的乘法更新），计算量随帧数增长，移动端实时不可行；分离质量有限——"BGM 低秩+人声稀疏"的假设在复杂音乐中不成立（人声也有持续元音、BGM 也有瞬态鼓点）；对宽立体声混音和复杂编曲效果差
传统 DSP 方案总结 五种传统 DSP 方法的共同局限是：无法有效处理人声与伴奏频谱重叠的场景。(L-R)*2 依赖空间位置差异，EQ 依赖频段差异，谱减法/维纳滤波依赖参考信号，RobustPCA/NMF 依赖低秩+稀疏假设——这些假设在现代音乐中均不完全成立。神经网络方法（MDX-Net 等）通过大量数据学习人声和伴奏的深层频谱-时间模式，能够在频谱重叠区域实现有效分离，这是传统 DSP 方法无法达到的。

1.4 技术选型全景：分离模型对比

在 1.3 节调研了传统 DSP 分离方案（中置提取、EQ、谱减法、维纳滤波、RobustPCA）后，本节聚焦神经源分离（Music Source Separation, MSS）领域的开源方案。选型的核心约束是移动端实时推理——模型必须能在手机 NPU/DSP 上以低于音频窗时长的延迟完成推理。以下对主流神经网络方案及传统 baseline 进行架构与可行性对比：

方案架构参数量分离质量 (SDR)移动端可行性本项目评估
(L-R)*2 中置提取 Mid-Side 矩阵运算，利用立体声空间位置差异 无参数 人声 SDR ≈ 1-4 dB（仅中置人声有效） 完美 零延迟零计算量 baseline 方案。仅严格中置人声有效，立体声展宽人声和中置乐器无法分离，质量不足
EQ 频段衰减 参数均衡器衰减 BGM 主导频段 无参数 人声 SDR ≈ 0-2 dB（频段重叠严重） 完美 原生 Equalizer 效果器 不适用。人声与 BGM 频段完全重叠，衰减 BGM 必伤人声，无法精确分离
谱减法 估计 BGM 功率谱后从混合谱中减去 无参数（需噪声估计） 人声 SDR ≈ 1-3 dB（有音乐噪声伪影） 中 需 FFT，计算量适中 不适用。需纯 BGM 参考段，BGM 非平稳时估计不准，音乐噪声伪影明显
维纳滤波 MMSE 最优线性滤波，需 BGM 参考/功率谱 无参数（需功率谱估计） 人声 SDR ≈ 2-5 dB（依赖参考质量） 中 需 FFT + 滤波 不适用。需要 BGM 参考信号，视频中无法获取，功率谱估计困难
MDX-Net U-Net 编解码 + 频域 2D 卷积，多尺度频谱输入 ~25-60M（取决于变体） 人声 SDR ≈ 7-9 dB（UVR MDX23 系列） 高 纯卷积网络，ONNX 导出友好，HTP EP 兼容 最终选择。频谱域 2D Conv 天然适配 NPU 张量加速器，静态 shape 导出稳定，HTP fp32 推理 0.11-0.25s/窗
Demucs 时域 U-Net + Transformer（HDemucs），时域卷积 + 自注意力 ~80-120M（hdemucs_mmi） 人声 SDR ≈ 8-10 dB（当前 SOTA 级） 中低 模型体积大，含 Transformer 层和 GLU，ONNX 导出后 QNN EP 兼容性差，移动端推理延迟高 质量最优但移动端不可行。Transformer 的动态计算图和大中间激活不适合 HTP 静态执行，CPU 推理单窗远超实时要求
Spleeter U-Net 编解码，频域 2D 卷积（基于 TensorFlow） ~10-25M（2stems/4stems/5stems） 人声 SDR ≈ 5-7 dB 中 架构与 MDX-Net 类似但质量较低，TensorFlow 模型需转 ONNX，转换后算子兼容性有损耗 可行但质量不足。Spleeter 是早期方案，分离质量明显低于 MDX-Net，且 TF→ONNX 转换链路增加不确定性
RobustPCA 非深度学习，低秩+稀疏矩阵分解（RPCA / REPET-SIM） 无参数（迭代优化） 人声 SDR ≈ 2-5 dB（仅适合重复结构强的音乐） 低 每帧需迭代求解，计算量随帧数增长，且假设"伴奏低秩+人声稀疏"在复杂音乐中失效 不适用。传统方法分离质量有限，无法处理人声与伴奏频谱重叠的场景，且迭代优化不适合实时流式处理
选型结论 MDX-Net 在"分离质量"与"移动端推理可行性"之间取得最佳平衡。其纯 2D 卷积架构是 HTP/NPU 张量加速器的理想工作负载，静态 shape 导出后 QNN EP 可完整卸载。Demucs 质量更优但移动端不可行，Spleeter 可行但质量不足，RobustPCA 不适用于复杂音乐的实时分离。

1.5 Android 音频架构知识

理解本项目的技术前提是掌握 Android 音频系统的层级关系。从 App 调用到硬件输出，音频数据经过以下层级：

App 层 第三方视频 App

1

2STFT/ISTFT 实现方案调研与对比

2.1 STFT 原理与参数选择

什么是短时傅里叶变换

短时傅里叶变换（Short-Time Fourier Transform, STFT）的核心思想是：对非平稳信号（如音乐、语音），先以一个有限长度的窗函数截取局部片段，假设该片段内信号近似平稳，再对加窗后的片段做傅里叶变换，得到该时刻的频率分布。通过窗函数在时间轴上以固定步长（hop）滑动，得到时频二维表示：

STFT{x(t)}(k, n) = Σ_{m=0}^{N-1} x(n·hop + m) · w(m) · exp(-j·2π·k·m/N)

其中 N 为窗长（FFT 点数），w(m) 为窗函数，hop 为帧移，k 为频率 bin 索引，n 为时间帧索引。STFT 的输出是复数谱，包含幅度和相位信息。

窗函数选择

窗函数决定了频谱泄漏（spectral leakage）和频率分辨率之间的权衡。主瓣越窄，频率分辨率越高；旁瓣越低，频谱泄漏越少。但两者不可兼得——窄主瓣通常伴随高旁瓣。以下对比三种常用窗函数：

窗函数主瓣宽度 (bin)最高旁瓣 (dB)COLA 条件适用场景
Hann (汉宁) 2 -31.5 50% 重叠时满足（hann + hann shifted by N/2 = 1） 本项目选择。平衡的主瓣宽度和旁瓣抑制，与 MDX-Net 训练配置一致，COLA 条件易于满足
Hamming (汉明) 2 -42.7 不严格满足 COLA（端点不为零，叠加后有微小波动） 语音编码、频谱分析。旁瓣更低但端点不为零，不适合精确重建
Blackman (布莱克曼) 3 -58.1 需 75% 以上重叠才近似满足 高动态范围频谱分析。旁瓣极低但主瓣宽、计算量大，不适合实时处理
periodic vs symmetric hann PyTorch 的 torch.hann_window(N, periodic=True) 生成的是周期窗：w(n) = 0.5·(1 - cos(2πn/N))，n ∈ [0, N-1]，第 N 个点（n=N）等价于 w(0)=0，即窗的首尾不重复。而 periodic=False（symmetric）使用 w(n) = 0.5·(1 - cos(2πn/(N-1)))，首尾均为 0。MDX-Net 训练时使用 periodic hann，因此本项目 JNI 层必须严格使用 periodic 版本以保证数值一致。

COLA（Constant Overlap-Add）条件

COLA 条件是 STFT 能够完美重建（perfect reconstruction）的数学前提：当窗函数以 hop 为步长滑动时，所有窗在每个时间点的叠加值为常数（通常为 1）。对于 hann 窗，当 hop = N/2（50% 重叠）时：

w(n) + w(n + N/2) = 0.5(1-cos(2πn/N)) + 0.5(1-cos(2π(n+N/2)/N))
= 0.5(1-cos(2πn/N)) + 0.5(1+cos(2πn/N)) = 1

本项目 hop=128，N=6144，重叠率为 1 - 128/6144 ≈ 97.9%，远超 COLA 所需的 50%，因此 COLA 条件充分满足。高重叠率的代价是计算量增大（每秒约 344 帧），但换来了更精细的时间分辨率和更平滑的重建。

N=6144 和 hop=128 的物理意义

在采样率 44.1kHz 下，关键参数的物理含义如下：

参数数值物理意义设计考量
FFT 点数 N 6144 窗时长 = 6144 / 44100 ≈ 139.3 ms MDX-Net 模型训练配置固定为 N=6144，提供 3072 个频率 bin，覆盖 0-22.05kHz
频率分辨率 fs/N = 44100/6144 ≈ 7.18 Hz/bin 每个频率 bin 覆盖约 7.18Hz 带宽 7.18Hz 的分辨率足以区分音乐中的相邻谐波（最低音 A1=55Hz 的半音间隔约 3.2Hz，在低频区 bin 覆盖略宽但可接受）
帧移 hop 128 帧时长 = 128 / 44100 ≈ 2.90 ms 高时间分辨率，每秒约 344 帧，确保瞬态信号（鼓点、辅音）的时间定位精度
重叠率 1 - 128/6144 ≈ 97.9% 相邻窗重叠 6016 个样本 远超 COLA 条件，WOLA 重建的 divider（hann² 累加）在绝大部分区域为常数，边界效应最小
Nyquist bin k = 3072（对应 22050Hz） 本项目丢弃 Nyquist bin，仅保留 k ∈ [0, 3072) MDX-Net 输入为 3072 频率 bin（不含 Nyquist），与训练一致；44.1kHz 音频在 22.05kHz 处能量极低，丢弃无感知影响

2.2 FFTW3 调研与移动端 FFT 库对比

移动端 FFT 库选型

STFT/ISTFT 的核心计算是 N=6144 点的复数 FFT，每秒约 344 帧 × 2（STFT+ISTFT）× 2（立体声）≈ 1376 次 FFT 变换。FFT 库的性能直接决定 STFT/ISTFT 阶段的耗时。以下对比移动端可用的 FFT 库：

库性能 (N=6144)精度Licensearm64 支持本项目评估
FFTW3 极优（运行时 plan 优化，SIMD/NEON 自动调度） 极高（long double 可选，float 精度 IEEE 754 严格） GPL v2（非商用免费） 完整支持 arm64-v8a，含 NEON 优化 最终选择。个人学习非商用场景 GPL 无冲突；数值精度与 PC 端 cuFFT/MKL 高度一致（corr=1.0）；prebuilt .so 集成简单
KissFFT 中等（纯 C 实现，无 SIMD 优化，N=6144 约为 FFTW 的 1/3-1/2 速度） 良好（float 精度） BSD（宽松） 支持 纯 C 可移植 可行但性能不足。1376 次/秒的 FFT 在无 SIMD 优化下可能成为瓶颈，且与 torch.stft 的数值差异需额外验证

N=6144 的特殊性 6144 = 2^11 × 3，不是纯 2 的幂。这排除了 pffft（仅支持 2 的幂），也使得某些仅支持 power-of-two 的简化 FFT 库不可用。FFTW3 支持任意复合长度（通过 Cooley-Tukey 混合基算法），是 N=6144 的理想选择。

  1. 交叉编译：使用 Android NDK 的工具链（--host=aarch64-linux-android），配置 CC=$NDK/toolchains/llvm/prebuilt/.../bin/aarch64-linux-androidXX-clang，启用 --enable-float --enable-neon 生成单精度 NEON 优化版 libfftw3f.so

  3. 链接配置：在 target_link_libraries 中链接 fftw3f，并在 build.gradle 的 packagingOptions 中确保 .so 被打包进 APK
  4. plan 缓存：FFTW3 的 fftwf_plan_dft_1d 在首次调用时进行 plan 优化（可能耗时数十毫秒），需在初始化阶段预创建 forward/backward 两个 plan 并复用，避免每帧重新规划

2.3 JNI 层实现（mdstft.cpp / FFTW3）

移动端 STFT/ISTFT 通过 JNI 调用 C++ 层 FFTW3 库实现，核心参数与布局设计如下：

STFT 参数

  • FFT 点数：N = 6144
  • 窗函数：periodic hann
  • center：True（两端 zero-pad）
  • 帧移：hop = 128
  • 频率 bin：k ∈ [0, 3072)（不含 Nyquist）

频域内存布局

index = ((ch*2 + reim) * 3072 + k) * 128 + t

ch: 声道(0/1), reim: 实部0/虚部1, k: 频率bin, t: 时间帧

ISTFT 参数

  • 变换方向：FFTW_BACKWARD
  • 归一化：手动 invN = 1/6144
  • 负频处理：k ≥ 3072 置零
  • 重建：hann / hann² WOLA 加权

频域内存布局设计理由

本项目采用的布局 ((ch*2+reim)*3072+k)*128+t 并非常规的 NCHW（batch,channel,height,width）或 NHWC 格式，而是一种面向 ONNX 输入和 FFT 访问模式的定制布局。设计考量如下：

  • ONNX 输入直接映射：MDX-Net 的输入形状为 (1, 4, 3072, 128)，其中 4 个通道 = [左声道实部, 左声道虚部, 右声道实部, 右声道虚部]。布局中的 (ch*2+reim) 恰好映射到通道维，k 映射到频率维（height=3072），t 映射到时间维（width=128）。STFT 输出可直接 memcpy 到 ONNX input tensor，无需额外的维度重排。
  • FFT 写入的缓存友好性：STFT 每帧计算后，需要写入该帧（固定 t）的所有频率 bin（k=0..3071）的实部和虚部。在布局中，固定 t 时，k 的变化对应连续内存（步长为 128），实部和虚部分别在两个 3072×128 的块中。写入时对每个 k 访问 base + k*128 + t，虽然步长为 128（非连续），但 reim 分离的设计使得实部/虚部各自在独立的连续区域内按 k 跨步访问，CPU 缓存预取器可识别固定步长模式。
  • 对比标准 NCHW 布局：若采用标准 NCHW (ch*2*3072*128 + reim*3072*128 + k*128 + t)，reim 维在最外层导致实部和虚部间隔 3072*128=393216 个 float，FFT 写入时实部和虚部的写操作在内存中相距过远，缓存命中率低。本布局将 reim 嵌入 ch 维（ch*2+reim），使同一通道的实部和虚部相邻（间隔 3072*128），但不同通道的同 reim 也相邻，更符合 ONNX 的通道组织方式。

center=True 的 zero-pad 边界处理

center=True 意味着在输入信号前后各补 N/2 = 3072 个零样本，使得第 0 帧的窗中心对齐输入信号的第 0 个样本。这与 PyTorch torch.stft(center=True) 的行为一致。具体处理：

  • padding 前：输入长度为 L，padding 后长度为 L + N（前后各 N/2）
  • 帧数：numFrames = (L + N - N) / hop + 1 = L/hop + 1（与 torch.stft 一致）
  • 边界帧：第 0 帧的窗覆盖 padding 区（3072 个零）+ 输入前 3072 个样本；最后一帧同理。这确保了信号起始和结束处的 STFT 不会因窗截断而产生伪影
  • ISTFT 重建：重建后需裁剪掉前后各 N/2 个样本，恢复原始长度 L

STFT 核心逻辑（C++）

// mdstft.cpp — STFT 核心
const int N = 6144;
const int HOP = 128;
const int NBINS = N / 2;  // 3072, 不含 Nyquist

// periodic hann 窗
for (int n = 0; n < N; n++) {
    window[n] = 0.5f * (1.0f - cosf(2.0f * M_PI * n / N));
}

// center=True: 输入前后各补 N/2 个零
// 每帧: 加窗 → FFTW_FORWARD → 写入频域缓冲
for (int t = 0; t < numFrames; t++) {
    for (int n = 0; n < N; n++) {
        fftIn[n] = input[t * HOP + n] * window[n];
    }
    fftw_execute(planForward);  // FFTW_FORWARD
    // 写入布局: ((ch*2+reim)*3072 + k)*128 + t
    for (int k = 0; k < NBINS; k++) {
        outRe[((ch*2+0)*NBINS + k)*HOP + t] = fftOut[k][0];
        outIm[((ch*2+1)*NBINS + k)*HOP + t] = fftOut[k][1];
    }
}

ISTFT 核心逻辑（C++）

// mdstft.cpp — ISTFT 核心
const float invN = 1.0f / 6144.0f;

for (int t = 0; t < numFrames; t++) {
    // 从频域布局读取，k >= 3072 置零（单边谱重建）
    for (int k = 0; k < N; k++) {
        if (k < NBINS) {
            fftIn[k][0] = inRe[((ch*2+0)*NBINS + k)*HOP + t];
            fftIn[k][1] = inIm[((ch*2+1)*NBINS + k)*HOP + t];
        } else {
            fftIn[k][0] = 0.0f;
            fftIn[k][1] = 0.0f;
        }
    }
    fftw_execute(planBackward);  // FFTW_BACKWARD
    // WOLA: 输出加权 hann / 累加 hann²
    for (int n = 0; n < N; n++) {
        float val = fftOut[n] * invN * window[n];
        outputAcc[t * HOP + n] += val;
        divider[t * HOP + n] += window[n] * window[n];
    }
}
// 最终输出 = outputAcc / divider

2.4 ISTFT 与 WOLA 原理

Weighted Overlap-Add (WOLA)

ISTFT 的标准重建方法是 Overlap-Add（OLA）：将每帧逆变换后的时域片段按 hop 位置叠加。但当分析窗（STFT 加的窗）和合成窗（ISTFT 加的窗）不同时，简单叠加会导致幅度失真。Weighted OLA（WOLA）通过引入归一化因子解决这一问题：

x_reconstructed(n) = Σ_t [ x_istft(t, n-t·hop) · w_synth(n-t·hop) ] / Σ_t [ w_synth(n-t·hop)² ]

其中 w_synth 是合成窗（本项目使用 hann），分子是各帧加权叠加，分母是窗平方的累加（divider）。当分析窗 = 合成窗 = hann 且满足 COLA 时，分母在信号中部为常数（约等于 N/(2·hop) 量级的常数），边界处逐渐过渡到 0。

hann / hann² 归一化的数学推导

本项目中，STFT 阶段对输入加了 hann 窗（分析窗），ISTFT 阶段对输出再加 hann 窗（合成窗），因此每帧的有效窗为 hann × hann = hann²。WOLA 的归一化 divider 就是所有帧 hann² 的累加：

divider(n) = Σ_t w(n - t·hop)²

对于 hann 窗 w(m) = 0.5(1 - cos(2πm/N))：
w(m)² = 0.25(1 - 2cos(2πm/N) + cos²(2πm/N))
      = 0.25(1 - 2cos(2πm/N) + 0.5(1 + cos(4πm/N)))
      = 0.375 - 0.5cos(2πm/N) + 0.125cos(4πm/N)

当 hop=128, N=6144 时（重叠率 97.9%），Σ_t cos(2π(n-t·hop)/N) ≈ 0（高频振荡项抵消）
因此 divider(n) ≈ Σ_t 0.375 = 0.375 × (N/hop) = 0.375 × 48 = 18（信号中部）

最终输出 = outputAcc / divider。在信号中部 divider ≈ 18（常数），在首尾边界处 divider 从 0 渐变到 18，天然实现了平滑的淡入淡出，无需额外处理。

为什么 FFTW_BACKWARD 不含 1/N

FFTW3 的设计遵循"FFTW_FORWARD 不缩放，FFTW_BACKWARD 也不缩放"的惯例——即 forward + backward 的结果是原始信号乘以 N。这是 FFTW 的有意设计（与 MATLAB 的 ifft 自动除以 N 不同），目的是让用户自行决定归一化位置（可以在 forward 后除以 N，或 backward 后除以 N，或各除以 √N）。本项目选择在 ISTFT 的 backward 后手动乘以 invN = 1/6144，与 PyTorch torch.istft 的归一化方式一致。

遗漏 invN 的后果 如果忘记乘以 invN，ISTFT 输出的幅度将是正确值的 6144 倍，音频完全削波（clipping）。这是 FFTW 新手最常见的错误之一。本项目通过与 PC torch.istft 对比验证（corr=1.0）确认了 invN 的正确性。

单边谱负频置零 vs Hermitian 对称

对于实数输入信号，其傅里叶变换满足 Hermitian 对称性：X[k] = conj(X[N-k])，因此只需存储正频率部分（k ∈ [0, N/2]）即可完整表示。但在重建时，两种处理方式存在细微差异：

方式负频处理Nyquist bin数学等价性
JNI：负频置零 k ∈ [3072, 6144) 全部置 0（实部=0, 虚部=0） k=3072 也置 0（丢弃 Nyquist） 等价于对正频率部分做"非对称"逆变换，输出为复数，取实部即为重建信号。由于负频全零，输出的虚部不为零但被忽略（FFTW_BACKWARD 输出实数数组的实部）
torch.istft：hermitian 自动构造 X[N-k] = conj(X[k]) 保留 k=3072（Nyquist bin，实数） 严格满足 Hermitian 对称，逆变换输出为纯实数，无需取实部

两者的核心差异在 Nyquist bin（k=3072）：JNI 丢弃它（置零），torch 保留它。对于 44.1kHz 采样的音频，Nyquist 频率为 22050Hz，超出人耳敏感范围（一般音乐在 16kHz 以上能量极低），因此丢弃 Nyquist bin 的感知影响为零。在 PC 侧通过裁剪掉 Nyquist bin（取前 3072 bins）后，两种方式达到数值一致（corr=1.0）。

为什么不能直接用 torch.istft hermitian 模式

torch.istft 在 center=True 时默认假设输入为 hermitian 对称谱（onesided 输入含 Nyquist bin），内部自动补全负频并执行归一化的逆变换。但本项目 JNI 层采用的是"单边谱 + 负频置零"方式，两者在 Nyquist bin 处理上不一致：

  • torch.istft 接收 3073 bins（含 Nyquist），内部构造 X[N-k] = conj(X[k])，Nyquist bin 作为实数参与变换
  • JNI ISTFT 接收 3072 bins（不含 Nyquist），负频全部置零，Nyquist 也置零

如果直接用 torch.istft 处理 JNI 输出的 3072-bin 谱，torch 会将第 3072 个 bin（k=3071）误当作 Nyquist，导致整个频谱偏移。因此 PC 侧必须手动构造完整的 6144 点频谱，将负频置零后做 torch.fft.ifft，再手动 WOLA，才能精确模拟 JNI 行为。

PC 侧手动构造完整频谱的代码

# mdx_pc_chain_sim.py — 模拟 JNI ISTFT 的手动完整频谱构造
import torch

def istft_like_jni(spec_re, spec_im, n_fft=6144, hop=128, window=None):
    """
    模拟 JNI 层 ISTFT 行为：
    - 输入: spec_re/spec_im 形状 (ch, 3072, T)，单边谱不含 Nyquist
    - 负频 (k >= 3072) 全部置零（包括 Nyquist）
    - FFTW_BACKWARD 等价于 torch.fft.ifft（不含 1/N，需手动乘）
    - WOLA: hann 加权输出 / hann² 累加 divider
    """
    nbins = n_fft // 2  # 3072
    ch, _, T = spec_re.shape

    # 构造完整 N 点频谱：正频来自输入，负频全部置零
    full_spec = torch.zeros(ch, n_fft, T, dtype=torch.complex64)
    full_spec[:, :nbins, :] = torch.complex(spec_re, spec_im)
    # k >= 3072 保持零（包括 Nyquist k=3072）

    # 逆 FFT（等价于 FFTW_BACKWARD，不含 1/N）
    time_frames = torch.fft.ifft(full_spec, dim=1).real  # 取实部
    time_frames = time_frames * n_fft  # FFTW_BACKWARD 不缩放，torch.fft.ifft 已含 1/N，需乘回 N

    # WOLA 重建
    output_len = (T - 1) * hop + n_fft
    output_acc = torch.zeros(ch, output_len)
    divider = torch.zeros(ch, output_len)

    for t in range(T):
        start = t * hop
        frame = time_frames[:, :, t] * window  # hann 合成窗
        output_acc[:, start:start+n_fft] += frame
        divider[:, start:start+n_fft] += window ** 2

    # 归一化，避免除零
    divider = torch.clamp(divider, min=1e-8)
    return output_acc / divider

2.7 逐环节验证数据与方法论

验证指标定义

本项目使用两个互补指标衡量数值对齐程度：

  • Pearson 相关系数（corr）：衡量两个信号的线性相关程度，公式为： 
    corr(x, y) = Σ[(x_i - x̄)(y_i - ȳ)] / √[Σ(x_i - x̄)² · Σ(y_i - ȳ)²]

    corr=1.0 表示完全线性相关（形状完全一致，允许常数增益和直流偏移），corr=0 表示不相关，corr<0 表示反相。corr 对整体增益差异不敏感，适合判断"波形形状是否一致"。

  • 最大差值（max diff）：max|x_i - y_i|，衡量两个信号的逐点绝对误差上限。max diff 对增益差异和直流偏移敏感，是 corr 的补充——corr=1.0 但 max diff 大说明存在增益偏差或直流偏移。

两个指标联合使用：corr 确保波形形状一致，max diff 确保幅度和直流一致。只有 corr≈1.0 且 max diff 在浮点误差范围内（1e-4 ~ 1e-5），才能确认逐位级对齐。

2.8 踩坑记录

坑 1：permute 轴交叉混叠

现象：PC 侧模拟链路中，将 torch.stft 输出转为 ONNX 输入后，模型推理结果与预期严重不符，分离输出 corr 降至 ≈ 0.001（接近随机噪声水平）。

排查过程：首先怀疑模型权重或 ONNX 导出问题，用固定输入测试模型输出正常。随后逐步检查 STFT 输出的可视化频谱图——发现频率轴和时间轴的图案完全错乱：原本应在时间轴上连续的谐波变成了在频率轴上的断续条纹。

根因：torch.stft 输出形状为 (batch, ch, freq, time, complex)，需要转为 ONNX 输入 (1, 4, freq, time)。错误的 permute(0,3,2,1) 将 freq 和 time 轴互换，导致模型看到的"频率维"实际是时间维，"时间维"实际是频率维。MDX-Net 的 2D 卷积在错误的维度上提取特征，输出完全无意义。

修复：正确的轴序为 permute(0, 1, 2, 3) 后拆分 complex 为实部/虚部通道，即保持 (batch, ch, freq, time) 不变，将 complex 的实部和虚部拆为两个通道。最终通道排列为 [ch0_re, ch0_im, ch1_re, ch1_im]，与 JNI 布局 (ch*2+reim) 一一对应。

验证：修正 permute 后，PC 模拟链路输出与 JNI+HTP 全链路输出 corr 从 ≈0.001 提升至 1.0。

坑 2：ISTFT 单边谱负频置零 vs torch.istft hermitian

现象：使用 torch.istft 直接处理 JNI 输出的 3072-bin 单边谱时，重建音频存在可感知的高频噪声和轻微相位失真，corr 约为 0.98（而非预期的 1.0）。

排查过程：对比 torch.istft 输入和 JNI ISTFT 输入的差异。发现 torch.stft(onesided=True) 输出 3073 bins（含 Nyquist），而 JNI 只输出 3072 bins。直接将 3072 bins 传给 torch.istft 时，torch 将第 3072 个元素（实际是 k=3071）误当作 Nyquist bin 处理，导致整个频谱的共轭对称构造错误。

根因：torch.istft 的 hermitian 模式假设输入包含 Nyquist bin（k=N/2），并据此构造负频 X[N-k] = conj(X[k])。当输入缺少 Nyquist bin 时，torch 仍按 hermitian 处理，将最后一个 bin 当作 Nyquist（实数），导致 k=3071 的虚部被丢弃，负频构造错误。

修复：放弃使用 torch.istft 的 hermitian 模式，改为手动构造完整 6144 点频谱（正频来自输入，负频全部置零），使用 torch.fft.ifft 做逆变换，再手动实现 hann/hann² WOLA。这精确模拟了 JNI 的"负频置零"行为。

验证：手动 ifft+WOLA 与 JNI ISTFT 输出 corr 达到 1.00000000，max diff ≈ 5e-5。

3.1.2 选择 ONNX Runtime 的核心理由

理由 1：模型原生 ONNX 格式，零转换成本

UVR-MDX-NET-Inst_HQ_3 模型本身就是 ONNX 格式（社区标准分发格式），PyTorch 训练后直接 torch.onnx.export 导出。若用 MNN/NCNN/TFLite，需经过 ONNX→目标格式的转换，可能遇到算子不兼容、精度损失、动态 shape 不支持等问题。零转换成本意味着模型可以直接使用，减少了引入额外误差的环节。

理由 2：QNN HTP EP 官方支持，Hexagon DSP 硬件加速

ONNX Runtime 提供官方 QNN Execution Provider，可直接利用高通 Hexagon HTP（DSP）进行推理加速——在 canoe（SM8850）设备上推理仅 0.11-0.25s/窗，相比 CPU EP 提速 20-60 倍。MNN 和 NCNN 均无 QNN HTP 支持，仅能使用 CPU/GPU，在 SM8850 上 CPU 推理需 4.4-7.4s/窗，无法达到实时要求。TFLite 的 NNAPI delegate 不直接支持 QNN HTP，且 NNAPI 在高通平台上的 DSP 调度不稳定，实际加速效果不可靠。

理由 3：PC/Android 同一模型文件，验证闭环简单

PC 端使用 ONNX Runtime CPU EP 生成参考基准（mdx_pc_chain_sim.py），Android 端使用同一 .onnx 文件 + QNN EP 进行推理，两端模型完全一致，便于数值对齐验证——本项目正是通过这种逐环节对比（corr=1.00000000）定位了 dump 起点不对齐和 permute 轴序错误等问题。若使用其他框架，PC 端需额外维护一套推理代码和模型格式，增加验证复杂度和引入不一致的风险。

理由 4：静态 shape 与算子兼容性

QNN EP 要求静态 shape 模型，ONNX Runtime 的静态 shape 导出成熟稳定（dim_value + ClearField dim_param）。MDX-Net 的纯卷积 U-Net 架构中所有算子（Conv2d、BatchNorm、LeakyReLU、ConvTranspose2d）均被 ONNX Runtime QNN EP 完整支持，无需自定义算子。而 MNN/NCNN 的转换器对某些算子（如 ConvTranspose2d 的特定 padding 模式）可能存在兼容性问题，需要额外调试。

3.1.3 开源社区因素

社区因素是辅助而非决定因素

ONNX 是目前开源音源分离社区（UVR、Demucs、MDX-Net）的标准模型分发格式，社区资源丰富、预训练模型直接以 ONNX 格式提供、问题排查容易。但这是辅助因素而非决定因素——即使不考虑社区，QNN HTP 官方支持和零转换成本这两个技术理由已足以决定选型。社区因素的价值在于降低了模型获取和问题排查的成本，但不是技术选型的根本依据。

3.1.4 不选其他框架的具体原因

  • MNN / NCNN：移动端 CPU 优化优秀（ARM NEON 汇编级优化），但无 QNN HTP 加速支持，仅能使用 CPU 推理。在 canoe（SM8850）上 CPU 推理需 4.4-7.4s/窗，远超 OLA 缓冲步进时长（2.21s），无法实时。此外模型转换（ONNX→MNN/NCNN）可能引入精度差异，增加数值验证复杂度。
  • TFLite：ONNX→TFLite 转换链路长（需经过 ONNX→TensorFlow→TFLite 两步转换），算子支持受限（MDX-Net 的某些算子可能不被 TFLite 原生支持），NNAPI delegate 在高通 DSP 上的调度不可靠（实际运行中可能回退到 CPU 或 GPU，加速效果不稳定）。
  • TensorRT：仅支持 NVIDIA CUDA 平台，移动端（Android 高通）完全不可用，不适用本项目硬件平台。
  • CoreML：仅支持 iOS/macOS 平台和 Apple ANE 神经引擎，不适用 Android 平台。

3.2 ONNX Runtime 与 EP 架构知识

什么是 Execution Provider

ONNX Runtime（ORT）是一个跨平台的机器学习推理引擎，其核心设计是可插拔的 Execution Provider (EP) 架构。EP 是 ORT 与特定硬件加速器之间的适配层，负责将 ONNX 计算图中的部分或全部算子分配到对应的硬件后端执行。ORT 本身提供 CPU EP 作为默认回退，其他 EP（如 CUDA、TensorRT、QNN、NNAPI、CoreML）通过注册机制扩展。

EP 的核心价值在于：同一份 ONNX 模型可以在不同硬件上通过切换 EP 实现硬件加速，而无需修改模型或推理代码。本项目中，同一份 MDX-Net ONNX 模型可以在 HTP EP（DSP 加速）和 CPU EP（通用处理器）之间切换，用于精度对照实验。

ORT 的 Graph Partitioning 机制

当 ORT 加载模型并注册了多个 EP 时，会执行图分区（graph partitioning）流程：

  1. 能力查询：ORT 遍历计算图中的每个节点（算子），依次询问每个已注册的 EP："你能执行这个节点吗？"
  2. 分区分配：每个 EP 声明自己能处理的节点子集。ORT 按 EP 注册优先级分配，高优先级 EP 先认领节点，剩余节点由低优先级 EP 或 CPU EP 处理。
  3. 子图编译：每个 EP 将分配到的连续节点簇编译为硬件特定的可执行单元（如 QNN EP 将子图编译为 HTA 指令序列）。
  4. 执行调度：运行时，ORT 在不同 EP 的子图之间调度数据传输（如 CPU↔DSP 的 DDR 拷贝），确保张量格式和布局匹配。

如果某个算子不被任何硬件 EP 支持，ORT 会自动回退到 CPU EP 执行（disable_cpu_ep_fallback=0 时）。这就是为什么"动态 shape + QNN EP + disable_cpu_ep_fallback=1"会失败——QNN EP 不支持动态 shape 的节点，而 CPU fallback 又被禁用，导致整个图无法执行。

QNN HTP EP 的工作原理

QNN（Qualcomm Neural Processing SDK）EP 是高通为 ONNX Runtime 提供的 Hexagon DSP 加速后端。其工作流程如下：

1
模型编译（离线/在线） — QNN EP 将 ONNX 子图转换为 QNN 中间表示（QNN IR），再编译为 Hexagon Tensor Accelerator (HTA) 可执行的指令序列。编译过程包含算子融合、常量折叠、内存规划等优化
2
HTA 指令生成 — 编译产物为 HTA 张量指令，包含 2D 卷积、激活函数、元素级运算等。HTA 是 Hexagon DSP 内的专用张量加速器，支持 fp16/fp32/int8 精度的张量运算
3
DSP 执行 — HTA 指令在 Hexagon DSP 上执行，利用 VTCM（Vector Tightly Coupled Memory）缓存减少 DDR 访问延迟。burst 性能模式下 DSP 运行在最高时钟频率
4
结果回传 — 推理完成后，输出张量从 DSP 本地内存回传到 DDR，ORT 继续执行后续子图（如有 CPU fallback 节点）

3.3 高通 Hexagon DSP / HTP 介绍

HTP v81 架构特点

Hexagon Tensor Processor（HTP）是高通在 Snapdragon 8 Gen 1 之后引入的专用 AI 加速单元，集成在 Hexagon DSP 内部。SM8850（骁龙 8 Elite）搭载的 HTP v81 是最新一代架构，核心特点包括：

HTA 张量加速器

Hexagon Tensor Accelerator 是专用的 2D 张量运算单元，原生支持卷积、池化、全连接等深度学习算子。相比 DSP 标量核执行卷积，HTA 的吞吐量提升一个数量级以上。MDX-Net 的 2D 卷积是 HTA 的理想工作负载。

VTCM 缓存

Vector Tightly Coupled Memory 是 HTA 的高速片上缓存，延迟远低于 DDR。本项目配置 vtcm_size_mb=8（vtcm8），用于缓存模型权重和中间激活。VTCM 大小直接影响推理性能——更大的 VTCM 减少 DDR 访问，但受限于芯片物理资源。

burst 性能模式

htp_performance_mode=burst 将 DSP 和 HTA 锁定在最高时钟频率，牺牲功耗换取最低延迟。对于实时音频处理场景，burst 模式确保推理延迟稳定在最低水平，避免动态调频导致的延迟波动。

为什么 MDX-Net 对 fp16 敏感

MDX-Net 的输出是频谱掩码（mask）——一个与输入频谱同形状的浮点张量，每个元素表示对应时频点的保留比例（0~1 之间）。掩码的精细数值直接决定分离质量：

  • 掩码的精细区分：在人声和伴奏频谱重叠的区域，掩码值可能在 0.3~0.7 之间微妙变化。fp16 的 ULP 在 0.5 附近约为 4.88e-4，虽然看似足够，但经过多层卷积的累积误差后，掩码的边界可能模糊化。
  • 量化误差累积：MDX-Net 是多层 U-Net 结构（编码器-解码器 + 跳跃连接），每层的 fp16 舍入误差会向下一层传播。对于 10+ 层的网络，误差可能从 1e-3 累积到 1e-2 量级，导致掩码在关键频率点出现可感知偏差。
  • 跳跃连接的敏感性：U-Net 的跳跃连接将编码器的低层特征直接加到解码器输出。如果编码器特征在 fp16 下丢失了精细细节（如高频弱信号），跳跃连接无法恢复，最终掩码缺失这些信息。
fp16 在本项目中的实际表现 初始实验中 HTP fp16 的 corr ≈ 0.01，看似是 fp16 精度不足导致。但后续 CPU EP 对照实验（不存在 fp16 问题）同样 corr ≈ 0.0117，推翻了这一假设。最终发现根因是 dump 起点不对齐。fp16 对 MDX-Net 的影响是理论上的敏感性，但在本项目的实际配置中，fp16 未被采用的原因更多是"未经验证"而非"已证明不可用"。HTP fp32 已满足性能和精度要求，无需冒险使用 fp16。

fp16 转换工具与 ON dump 分析

在尝试 fp16 方案时，使用 onnxruntime.transformers.float16 工具将 fp32 ONNX 模型转换为 fp16：

from onnxruntime.transformers import float16
from onnx import load_model, save_model

model = load_model("mdx_net_fp32.onnx")
fp16_model = float16.convert_float_to_float16(
    model,
    keep_io_types=True,       # 保持输入输出为 fp32，内部算子转为 fp16
    op_block_list=["Sqrt"]    # 排除对 fp16 敏感的算子
)
save_model(fp16_model, "mdx_net_fp16.onnx")

转换后通过 ONNX Runtime 的 InferenceSession 运行固定输入，dump 每一层的输出张量，与 fp32 模型的对应层输出对比。分析发现：

  • 前 3 层卷积的输出差异在 1e-3 量级（fp16 舍入误差）
  • 经过 5 层后差异扩大到 1e-2
  • 最终掩码输出的差异在某些时频点达到 0.1 以上

这一分析确认了 fp16 的误差累积趋势，但由于后续发现 dump 对齐问题才是 corr≈0.01 的主因，fp16 的真实影响未被完全量化。最终选择 fp32 以消除精度风险。

CPU EP 的 XNNPACK 后端

ONNX Runtime 的 CPU EP 在 Android arm64 平台上默认使用 XNNPACK 作为推理后端。XNNPACK 是 Google 开发的高性能神经网络算子库，针对 ARM NEON 指令集优化：

  • XNNPACK 对 2D 卷积使用 implicit GEMM + NEON 向量化，单线程性能优于通用实现
  • 支持多线程（通过 sessionOptions.setIntraOpNumThreads(N) 配置），但 MDX-Net 的大特征图（3072×128）受限于内存带宽，多线程扩展性有限
  • CPU EP 单窗推理 4.4-7.4 秒，其中绝大部分时间消耗在编码器的前几层大通道卷积上

CPU EP 在本项目中仅作为精度对照使用——其推理结果与 PC 端 CPU 推理应完全一致（同为 fp32，同为 XNNPACK/MKL 类后端），用于验证"EP 本身是否引入数值差异"。

3.7 精度排查完整推理链

从最初的 corr≈0.01 到最终的 corr=1.0，排查过程经历了多次假设的建立与推翻。以下是完整的逻辑推理链：

转折点 1：fp16 是元凶？

观察：HTP fp16 推理输出与 PC CPU 基准对比 corr ≈ 0.01，几乎不相关。

假设 A：fp16 的 10 位尾数精度不足，MDX-Net 掩码的精细数值在半精度下丢失，导致分离输出完全错误。

行动：关闭 fp16，切换到 HTP fp32。

转折点 2：fp32 也不对齐 → fp16 假设动摇

观察：HTP fp32 推理输出 corr ≈ 0.45，虽然比 fp16 好，但远未达到预期的 1.0。

推理：如果 fp16 是唯一问题，fp32 应该接近 1.0。fp32 仍有 0.55 的差距说明存在其他差异源。可能的原因：(a) HTP EP 的 fp32 实现本身有数值偏差；(b) 输入数据与 PC 侧不一致；(c) 模型导出时存在算子差异。

行动：设计 CPU EP 对照实验，在同一设备上用 CPU EP 推理同一模型。

转折点 3：CPU EP 也偏离 → 彻底推翻 fp16 假设

观察：CPU EP 推理结果与 PC CPU 对比 corr ≈ 0.0117，比 HTP fp32 还差！

关键推理：CPU EP 不存在 fp16 问题（纯 fp32 推理），也不存在 HTP 硬件特有的数值偏差（XNNPACK 是标准 CPU 后端）。如果 CPU EP 都偏离，那么差异源不可能是 EP 本身的数值精度，而必然是输入数据或验证方法的问题。

新假设 B：App 端 dump 的输入数据与 PC 侧使用的输入数据不对齐——dump 起点不是处理起点，导致 PC 用 A 段音频推理，App 用 B 段音频推理，两者输出自然不相关。

转折点 4：发现 dump 起点不对齐

排查：检查 App 端 dump 逻辑。发现开启 dump 时，OLA 缓冲中可能已有之前处理的陈旧数据，dump 文件的第一个样本不等于 OLA 链当前处理的第一个样本。此外，AudioPlaybackCapture 的启动时序也可能导致 dump 捕获到缓冲中的旧数据。

验证：在 setDumpEnabled(true) 时强制调用 resetOla()，清空所有 OLA 缓冲和输入缓冲，确保 dump 起点 = 处理起点。同时修正 PC 侧 permute 轴序。

转折点 5：修正后 corr=1.0

结果：修正 dump 对齐和 permute 后，HTP fp32 与 PC CPU 推理输出 corr = 1.0，max diff = 0.000251。CPU EP 同样达到 corr=1.0。

最终结论：ONNX Runtime 的 QNN HTP EP 在 fp32 模式下数值精确，与 PC CPU 逐位一致。此前所有低 corr 结果均由数据对齐问题（dump 起点、permute 轴序）导致，与 EP 本身无关。

QNN EP 仍按动态 shape 处理，拒绝加载模型		 ONNX 的 TensorShape 中，dim_param 和 dim_value 是互斥字段，但如果两者同时存在（未正确清除 dim_param），ONNX Runtime 和 QNN EP 的解析器可能优先识别 dim_param，将维度视为动态。这导致"看起来设了固定值，实际仍是动态"的假静态状态 导出后使用 onnx.checker 验证模型，确保所有维度只有 dim_value 无 dim_param；或使用 onnx.shape_inference.infer_shapes 后手动 ClearField("dim_param")

VTCM 大小对性能的影响

  • vtcm=4MB：MDX-Net 的部分中间激活无法全部驻留 VTCM，需要频繁与 DDR 交换数据，推理延迟可能增加 20-40%
  • vtcm=8MB（本项目配置）：能够缓存大部分层的权重和激活，DDR 访问显著减少，是性能和资源的平衡点

4.1 MDX-Net 模型架构与输入张量

UVR-MDX-NET-Inst_HQ_3_b1 是基于 U-Net 编解码器架构的神经源分离模型，专门针对立体声音乐的人声/伴奏分离任务设计。理解其网络结构是分析 seg 参数影响的前提。

U-Net 编解码器架构

模型采用经典的 U-Net 对称结构，由编码器（下采样路径）、瓶颈层和解码器（上采样路径）组成，各层级之间通过跳跃连接（skip connection）传递多尺度特征：

  • 编码器：多级 2D 卷积 + stride=2 下采样，逐步压缩时间-频率二维特征图的空间分辨率，同时增加通道数，提取从局部纹理到全局结构的多尺度语义特征。
  • 瓶颈层：在最低分辨率处进行深度特征变换，捕获长程频谱-时间依赖关系。
  • 解码器：多级转置卷积 + stride=2 上采样，逐步恢复空间分辨率，与编码器对应层的跳跃连接特征拼接，融合细节与语义信息。
  • 输出头：1×1 卷积将多通道特征映射为与人声/伴奏对应的掩码谱（mask），与输入混合谱相乘得到分离结果。

输入张量 (1, 4, 3072, 128) 的维度含义

维度 0：batch = 1

单样本推理。移动端流式处理每次仅送入一个音频块，batch 固定为 1。

维度 1：channels = 4

4 个通道对应立体声混合谱的实部/虚部展开：ch0_real, ch0_imag, ch1_real, ch1_imag（左声道实部、左声道虚部、右声道实部、右声道虚部）。模型在频域直接处理复数谱的实虚部分离表示，而非幅值-相位。

维度 2：freq = 3072

频率维固定为 3072 bins，来自 FFT 点数 N=6144 的单边谱（取前 3072 bins，不含 Nyquist bin 3072）。覆盖 0 Hz ~ 22.05 kHz 的完整可听频率范围。

维度 3：time = seg = 128

时间维为 seg 个 STFT 帧。在 hop=1024、44.1kHz 下，128 帧对应约 128 × 1024 / 44100 ≈ 2.97 秒的音频上下文。这是 seg 参数的核心含义——模型每次推理所能"看到"的时间窗口长度。

为什么是 (1,4,3072,128) 而不是 (1,2,3072,1024)？

MDX-Net 在频域以 2D 特征图方式处理立体声复数谱。4 通道是实虚部×立体声的展开结果，这是模型训练时固定的输入格式，不可更改。频率维 3072 由 FFT 点数决定，覆盖完整可听频段。时间维 seg 则是可配置的分段长度——它不是 1024（那是 hop 长度，即相邻 STFT 帧的采样间隔），而是每次送入模型的帧数。将 seg 设为 128 意味着每次推理处理 128 帧、约 2.97 秒的音频块，而非 1024 帧（那将需要约 23.8 秒的上下文，计算量和内存均不可接受）。

4.2 seg 参数原理与最小尺寸约束

seg（segment）是模型输入张量的时间维长度，即每次 U-Net 前向推理处理的 STFT 帧数。在流式处理中，完整音频的谱图沿时间维被切分为若干个 seg 长度的帧块，逐块送入模型推理，再通过 OLA（Overlap-Add）拼接回完整输出。

U-Net 下采样导致的最小尺寸约束

U-Net 编码器中每级 stride=2 的卷积会将时间维尺寸减半。若网络包含 n 级下采样，则输入时间维必须至少为 2^n，否则在某一级下采样后特征图尺寸变为 0 或小于卷积核要求，触发 Conv Invalid input shape 错误。

以 MDX-Net 的 U-Net 结构为例，假设编码器包含 4 级 stride=2 下采样：

理论最小尺寸 = 2^4 = 16

但实际还需考虑卷积 padding 和跳跃连接的形状匹配：
- seg=16 → 经过 4 次下采样后时间维 = 16/16 = 1
  某些层的卷积核（如 3×3）在尺寸为 1 时仍可能因 padding 策略不匹配而失败
  实测错误：Invalid input shape {1,192}（中间特征图通道×空间维度异常）

- seg=32 → 经过 4 次下采样后时间维 = 32/16 = 2
  满足所有卷积层的最小空间要求，推理正常

- seg=8 → 经过 3 次下采样后时间维 = 8/8 = 1，第 4 次下采样前已不满足
  实测错误：Invalid input shape {1,384}
seg 工程下限 = 32

seg=16 和 seg=8 均触发 ONNX Runtime 的 Conv Invalid input shape 错误（分别在节点 553_nchwc 和 532_nchwc），根因是 U-Net 多级下采样后时间维特征图尺寸小于卷积核最小要求。seg=32 是实测可运行的最小值，但分离质量已有可感知下降（corr=0.9948）。

扫描方法论

  1. 固定输入音频：使用同一首测试素材（yimeng 朗诵，44.1kHz 立体声），确保对比公平。
  2. 逐 seg 导出静态模型：基于原始 ONNX 模型，通过修改 graph input/output 的 dim_value 将时间维固定为目标 seg 值，同时 ClearField 动态维度标记（dim_param 置空），导出为独立的静态 ONNX 文件。

4.4 seg 大小对分离质量的影响分析

为什么 seg 越小 corr 越低？

U-Net 的分离能力依赖于对音频时间上下文的理解。人声和伴奏的区分不仅取决于局部频谱特征，还依赖于更长时间尺度上的旋律走向、节奏模式和和声结构。当 seg 减小时，模型每次推理能看到的时间窗口缩短，导致：

  • 高频泛音丢失：人声的高频泛音（如唇齿音 /s/、/t/ 的能量集中区）在短上下文中容易被误判为伴奏的高频噪声而抑制，导致人声发闷、细节丢失。
  • 瞬态模糊：打击乐瞬态（鼓点、拨弦）需要前后文来定位起始点。短上下文中模型无法准确判断瞬态归属，导致伴奏轨中的瞬态被模糊或泄漏到人声轨。
  • 音乐噪声（musical noise）：频域掩码在短上下文中产生孤立的、随时间闪烁的频谱点，ISTFT 后表现为"水声"或"金属声"伪影。seg 越小，掩码的时间连续性越差，音乐噪声越明显。
  • 和声判断失误：和弦的识别需要多个音符的持续时间，短窗口可能只捕获到和弦的一部分，导致掩码错误。

4.5 真机部署 seg128 的详细理由

真机最终采用 seg=128 的静态导出模型，输入形状 (1, 4, 3072, 128)，模型文件大小 66,764,970 bytes（约 63.7 MB）。以下从四个维度详细阐述选择理由。

理由一：质量保障——最长时间上下文

seg128 提供约 2.95 秒的时间上下文，是所有可行 seg 值中最长的（seg256 虽质量更高但单窗计算量过大，且移动端 OLA 缓冲管理复杂）。扫描实验表明 seg128 的分离输出与最大上下文参考（seg256）的 corr 接近 1.0，是质量与可行性的最佳平衡点。seg 减小到 64/32 时 corr 分别下降 0.0024 和 0.0052，对人声分离的细节（呼吸声、唇齿音、高频泛音）有可感知影响。

理由二：HTP 加速抵消延迟

seg128 的单窗计算量最大，但在 canoe 设备的 QNN HTP EP 上推理仅需 0.11 - 0.25 秒，远小于音频窗时长（2.95s），推理实时比（RTF）约为 0.04 - 0.08，延迟完全在 OLA 缓冲可覆盖范围内。即使考虑 STFT/ISTFT 前后处理开销，端到端单窗处理也远低于 2.21s 的窗口步进时长，不会产生时序漂移。

理由三：静态 shape 约束与导出稳定性

QNN HTP EP 要求模型输入为静态 shape（动态 shape 支持不完善，禁用 CPU fallback 后直接推理失败）。seg128 是模型原始训练配置的标准分段大小，导出最稳定，无需额外适配。静态导出的具体操作：

# mdx_pc_seg_sweep.py — 静态 shape 导出
import onnx

def export_static(seg, out_path):
    m = onnx.load(BASE_MODEL)
    for g in (m.graph.input, m.graph.output):
        d = g[0].type.tensor_type.shape.dim
        d[0].dim_value = 1       # batch 固定为 1
        d[0].dim_param = ''      # ClearField：清除动态维度标记
        d[3].dim_value = seg     # 时间维固定为 seg
        d[3].dim_param = ''      # ClearField：清除动态维度标记
    onnx.checker.check_model(m)
    onnx.save(m, out_path)
"假静态"导出陷阱

仅设置 dim_value 而不 ClearField dim_param 会导致 dim_param 与 dim_value 共存，ONNX Runtime 仍按动态 shape 处理，QNN EP 拒绝加载。必须同时将 dim_param 置空字符串，才能被运行时识别为真正的静态 shape。

理由四：模型体积与参数量分析

模型文件 66,764,970 bytes 的构成：

  • 权重参数：fp32 精度下约占文件体积的 95% 以上。粗略估算参数量 ≈ 66.7MB / 4 bytes ≈ 16.7M 参数（含卷积核、偏置、归一化层参数等）。
  • 计算图结构：ONNX graph 的节点定义、张量形状、元数据等，约占数 MB。
  • 与 seg 无关：模型权重体积仅由网络结构（层数、通道数、卷积核大小）决定，与输入 seg 大小无关。seg64/seg32 的模型文件体积与 seg128 完全相同（仅 input/output 的 dim_value 不同，差异可忽略）。

63.7 MB 在现代 Android 设备上完全可接受（APK 总大小约 140.5 MB，含 FFTW3 + ONNX Runtime + 模型）。

4.7 流式处理参数体系深度解析

基于 seg128 模型，OLA 流式处理的核心参数构成一个严密的数学体系。每个参数都有明确的物理意义和推导关系。

参数值 (samples)等效时长 (@44.1kHz)物理意义与推导
CHUNK_SAMPLES 130,048 ≈ 2.95s 每次送入模型的音频块大小。推导：CHUNK = HOP × (seg - 1) = 1024 × 127 = 130048。减 1 是因为 center=True 的 STFT 在 chunk 前后各补 N_FFT/2=3072 个零，总长度 = 130048 + 6144 = 136192，帧数 = (136192 - 6144)/1024 + 1 = 128 = seg。
TRIM 3,072 ≈ 69.7ms 每侧裁剪样本数，等于 N_FFT/2。STFT 的 center=True 在 chunk 两端补零，导致 ISTFT 重建后 chunk 首尾各 N_FFT/2 个样本受零填充边界效应影响（卷积边缘效应，表现为信号衰减或畸变）。TRIM 裁剪掉这些不可靠区域，只保留中间有效部分。
GEN_SIZE 123,904 ≈ 2.81s 模型有效输出长度。推导：GEN_SIZE = CHUNK - 2 × TRIM = 130048 - 6144 = 123904。即 chunk 去掉两侧 TRIM 后的中间有效区域。
STEP_SAMPLES 97,536 ≈ 2.21s 相邻窗口的步进样本数。推导：STEP = CHUNK × (1 - OVERLAP) = 130048 × 0.75 = 97536。即每个新窗口相对于上一个窗口的起始位置偏移。STEP 决定了输出帧率和实时性要求。
输出重叠区 26,368 ≈ 598ms 相邻窗口有效输出的重叠长度。推导：重叠 = GEN_SIZE - STEP = 123904 - 97536 = 26368。重叠区占 GEN_SIZE 的 26368 / 123904 ≈ 21.3%。

重叠区交叉淡化设计

OLA（Overlap-Add）的核心是相邻窗口在重叠区进行加权交叉淡化（crossfade），确保拼接处无爆音、相位连续：

  • 窗函数：使用 symmetric Hanning 窗对每个窗口的 ISTFT 输出进行加权，窗长 = CHUNK_SAMPLES。在重叠区内，前一窗的尾部权重从 1 渐降至 0，后一窗的头部权重从 0 渐升至 1，两者之和恒为 1（Hanning 窗的 Constant Overlap-Add 性质）。
  • 重叠占比 21.3%：这是由 75% 的窗口步进比（STEP/CHUNK=0.75）和 TRIM 裁剪共同决定的。21.3% 的重叠率（约 598ms）足够长，可实现平滑的交叉淡化，避免窗口边界处的不连续；同时又不会过长导致 OLA 缓冲管理复杂和内存浪费。
  • WOLA 归一化：输出缓冲累加各窗口的 hann 加权值，同时累加 hann² 作为归一化因子（divider），最终输出 = accum / divider。这确保了重叠区的幅值正确，不会因多窗叠加而产生增益提升。
参数体系数学关系总览 CHUNK = HOP × (seg - 1) = 1024 × 127 = 130048
TRIM = N_FFT / 2 = 6144 / 2 = 3072
GEN_SIZE = CHUNK - 2 × TRIM = 130048 - 6144 = 123904
STEP = CHUNK × 0.75 = 97536
重叠 = GEN_SIZE - STEP = 26368（占 GEN_SIZE 21.3%，约 598ms）

5.1 验证方法论与指标定义

什么是端到端全链路验证

端到端全链路验证是指从音频输入的最源头（系统音频捕获）到最终输出的最末端（AudioTrack 回放），对完整处理管线进行一次性数值校验，而非仅验证单个模块（如只验证 STFT 或只验证模型推理）。全链路验证能够发现模块间接口不匹配、时序错位、缓冲污染等单模块测试无法暴露的问题。

为什么需要 PC 参考基准

移动端 App 的处理链路包含 JNI STFT、ONNX 推理、JNI ISTFT、OLA 拼接、重采样等多个环节，每个环节都可能引入数值偏差。为判断偏差来源，需要在 PC 端构建一条"复刻链路"（使用相同参数、相同模型、相同算法），以 PC 输出作为参考基准（ground truth），再将 App 真机输出与 PC 基准逐样本对比。PC 端使用 ONNX Runtime CPU EP 推理，结果稳定可复现，且可通过 torch.stft/istft 或手写 rfft/ifft 精确控制每一步数值。

Pearson 相关系数 (corr)

Pearson 相关系数衡量两个信号波形的线性相关程度，是全链路验证的核心指标：

corr(x, y) = Σ[(x_i - x̄)(y_i - ȳ)] / sqrt[Σ(x_i - x̄)² × Σ(y_i - ȳ)²]
corr 值含义音频听感
1.0完全正相关，波形完全一致（允许整体增益差异）完全相同
> 0.99高度相关，微小数值偏差不可感知或极轻微差异
0.95 - 0.99较高相关，存在可测量偏差精细听感可察觉
0.8 - 0.95中等相关，明显偏差明显可感知
0不相关完全不同
-1.0完全负相关，波形反相反相（声学抵消）

corr 对整体增益差异不敏感（只看波形形状），因此需要配合 RMS 电平差来评估幅值一致性。

RMS 能量差 (dB)

均方根（RMS）能量差衡量两个信号的整体响度差异，计算公式：

RMS(x) = sqrt(mean(x²))
RMS_dB(x) = 20 × log10(RMS(x))
RMS 差值 = RMS_dB(ref) - RMS_dB(test) = 20 × log10(RMS_ref / RMS_test)

人耳对响度的可感知阈值约为 1 dB（在安静环境中经过训练的耳朵可感知 0.5 dB 差异）。RMS 差小于 0.1 dB 时，人耳完全无法区分响度差异。

per-2s 分段分析

将全链路输出按每 2 秒切分为若干段，逐段计算 corr，用于检测时序漂移（temporal drift）。如果整体 corr 高但后段 per-2s corr 持续下降，说明输出随时间逐渐与参考基准错位——这是推理延迟累积导致的典型特征。per-2s 分析能将"算法质量问题"与"时序漂移问题"区分开来：前者表现为全段均匀偏低，后者表现为前段高、后段逐渐衰减。

5.3 全链路验证流程

全链路验证遵循"PC 生成参考 → 真机捕获处理 → dump 对齐 → 数值对比"的四阶段流程：

1
PC 端生成参考音频 — 将同一输入音频（48kHz 立体声 PCM）经 PC 复刻链路处理：线性重采样 48k→44.1k → STFT（手写 rfft，与 JNI 逐项对齐）→ MDX-Net ONNX CPU 推理 → ISTFT（单边置零 + hann WOLA）→ OLA 拼接 → vocals = mix - accomp（gain=0）→ 重采样 44.1k→48k，输出 pc_vocals.wav 作为参考基准
2
设备端播放并捕获处理 — 在目标设备上播放同一音频（通过视频 App 或本地播放器），App 通过 AudioPlaybackCapture 捕获系统音频，经 JNI STFT → ONNX 推理（HTP 或 CPU EP）→ JNI ISTFT → OLA → AudioTrack 回放，同时通过 setDumpEnabled 将输入和输出 dump 为 PCM16 WAV 文件
3
adb pull 提取 dump 文件 — 将设备端的 input_dump.wav（捕获的原声）和 output_dump.wav（处理后的输出）通过 adb pull 提取到 PC
4
PC 脚本对齐起点 — mdx_dump_verify.py 读取 App input_dump，经相同 PC 复刻链路生成参考输出；在 ±5s 范围内以 9600 采样步进粗对齐、再以 960 采样步进细对齐，找到最大化 corr 的最佳偏移量（best offset）
5
计算 corr / RMS / per-2s — 在最佳偏移对齐后，逐通道计算 Pearson corr、RMS dB 差值、per-2s 分段 corr，输出验证报告
对齐的必要性

App 输出的 dump 起点相对于 PC 参考存在固定延迟（首窗采集 + 模型加载 + 推理 + 播放启动，约 2-3 秒）。如果不做偏移对齐直接对比，corr 会接近 0。验证脚本通过滑动窗口搜索最佳偏移（±240000 samples @48k = ±5s），消除固定延迟后再计算质量指标。

per-2s corr 的衰减呈近似指数趋势：前 3 段（0-6s）基本平坦（0.994+），第 4-5 段（6-10s）开始线性下降（0.969 → 0.93），第 6-7 段（10-14s）加速下降（0.909 → 0.84），第 8 段（14-16s）骤降至 0.45。骤降点对应累积延迟超过输入时长的时刻——此时 App 输出的内容在 PC 参考中已无对应片段，corr 失去意义。

5.6 差异根因深度分析

全链路验证过程中排查并修复了 4 个关键差异源。以下按"现象 → 排查 → 根因 → 修复 → 验证"结构逐一分析。

根因一：PC 脚本 permute 轴序错误

阶段详情
现象PC 模拟链路输出与 App 输出 corr 极低（≈ 0），频谱图完全错乱，分离结果毫无意义。
排查逐层对比 PC 脚本与 JNI 层的频域内存布局。JNI 布局为 ((ch*2+reim)*3072 + k)*128 + t（频率 k 为行、时间 t 为列），而 torch.stft 输出为 (batch, ch, freq, time, complex)。PC 脚本在将 torch.stft 输出转为 ONNX 输入 (1,4,freq,time) 时，使用了错误的 permute。
根因permute(0,3,2,1) 将频率轴与时间轴交叉互换。正确顺序应为 permute(0,3,1,2)：先将 complex 维（dim=3）提到通道维位置，再保持 ch(freq,time) 的排列。错误的 permute 导致模型看到的"频谱"实际上是时间-频率转置后的乱码，模型输出完全无意义。
修复将 permute 改为 permute(0,3,1,2)，并最终弃用 torch.stft，改写为手写 float64 rfft，从根源上避免布局转换错误。
验证修复后 PC 模拟链路的 STFT 输出与 JNI STFT 输出 corr 从 ≈0 提升至 1.00000000，max diff = 3e-5。

根因二：PC 脚本 ISTFT 差异（Hermitian vs 负频置零）

阶段详情
现象PC 端 STFT→ISTFT 自洽往返重建 corr = 0.999976 而非 1.0，且 PC 复刻链输出与 App 输出存在系统性波形偏差。
排查对比 JNI ISTFT 与 torch.istft 的负频处理策略。JNI 层采用单边谱（k∈[0,3072)），ISTFT 时手动将 k≥3072（含 Nyquist bin 3072）置零后做 FFTW_BACKWARD。torch.istft 默认假设输入为 hermitian 对称谱（含 Nyquist bin 共 3073 bins），内部自动补全负频共轭。
根因Nyquist bin（k=3072，对应 22.05kHz）的处理差异：JNI 丢弃 Nyquist（单边谱只取前 3072 bins），torch.istft 保留并按 hermitian 对称补全负频。这导致两者在高频端的重建结果存在微小但系统性的偏差，累积后 corr 无法达到 1.0。
修复在 PC 侧裁剪掉 Nyquist bin（取前 3072 bins），改用手写 ifft（torch.fft.ifft，k≥3072 置零）替代 torch.istft，与 JNI 的单边谱 + 负频置零策略完全对齐。
验证修复后 PC STFT→ISTFT 往返重建 corr 提升至 1.0，PC 复刻链与 App 输出的 corr 显著提升。

根因三：App OLA 竞争 bug（writeFrame 提前推进）

阶段详情
现象App output 呈"段-静音-段"结构——每 1-2 秒有声后跟随 0.5-1 秒静音，全链 corr 卡在 0.02-0.53 之间无法提升。音频听感为断续的碎片。
排查追踪 OLA 缓冲的 writeFrame 和 playFrame 推进时序。发现窗口提交时 writeFrame 立即 += STEP，导致 playable（= writeFrame - TRIM）在推理完成前就已增长。playAvailableMdxOutput 在推理完成前消费 [playFrame, playable) 区间，此时 OLA 缓冲中该区间全为 0（推理尚未写入），于是将静音写入 dump 并推进 playFrame。等推理完成 addToOla 写入真实内容时，该区间已被跳过，每窗只剩尾部碎片被输出。
根因writeFrame 的推进时机错误：应在推理完成、真实内容写入 OLA 缓冲后推进，而非在窗口提交时提前推进。提前推进导致播放逻辑消费了尚未填充的缓冲区域。
修复将 writeFrame 移到 addToMdxOlaLocked 内部推进（推理完成回调中），playable 只在内容真实就绪后增长。配合 epoch 世代计数机制，确保在途推理结果不会污染 reset 后的新流。
验证修复后 App 输出每窗完整、无静音段，全链 corr 从 0.53 跃升至 0.9877（Redmi 首轮），后续 canoe 达到 0.9934/0.9947。

根因四：SET_DUMP 起点不对齐

阶段详情
现象App dump 数据与 PC 输入对比 corr ≈ 0.01，即使排除固定延迟后仍无法对齐。HTP fp16 时 corr≈0.01，关闭 fp16 改用 HTP fp32 后 corr≈0.45，改用 CPU EP 后 corr≈0.0117——三种 EP 都严重偏离，疑似 EP 精度问题。
排查对比 dump input 的起始样本与 App 实际处理的起始样本。发现开启 dump 时 OLA 缓冲中已有之前处理残留的陈旧数据（或前置 TRIM 静音未初始化），dump 文件的第一个样本不等于 OLA 链处理的第一个样本。
根因dump 启动时 OLA 缓冲状态未重置。如果此前有过处理（或缓冲未清零），dump 起点包含陈旧数据，导致 PC 侧以 dump input 为输入生成的参考输出与 App 实际处理的输入在时间轴上错位。这一问题与 EP 无关——三种 EP 都偏离是因为输入数据本身就不对齐。
修复setDumpEnabled(true) 时调用 resetOla()，清空所有 OLA 缓冲（mdxOlaBuffer、mdxOlaDivider）和输入缓冲（mdxInput44），并立即 initMdxOla（前置 TRIM silence），确保 dump input 起点 == 处理起点。
验证修复后 HTP fp32 与 PC CPU 对比 corr 达到 1.0，证明此前的低 corr 完全是 dump 起点不对齐导致，EP 本身数值精确。这一修复也推翻了"fp16 导致差异"的早期假设。

根因五：Redmi 推理延迟（硬件限制，非 bug）

阶段详情
现象Redmi 全链 corr 后段衰减至 0.826/0.830，per-2s 从 1.0 降至 0.45。
排查前 5 段 corr 0.93-1.0 证明算法无质量问题；推理耗时测量显示 CPU EP 单窗 4.4-7.4s，远超窗口步进 2.21s。
根因CPU EP 推理速度跟不上实时要求，OLA 缓冲逐渐排空，输出时序漂移。这是硬件性能限制，非代码 bug。
修复无法通过软件修复，需 HTP 硬件加速。canoe 设备使用 QNN HTP EP 后推理降至 0.11-0.25s/窗，完全消除漂移。
验证canoe HTP 全链 corr L=0.9934/R=0.9947，per-2s 全程 >0.99，无衰减。
排查链 corr 提升轨迹

HTP fp16 (≈0.01) → 关 fp16 HTP fp32 未对齐 (≈0.45) → CPU EP 对照 (≈0.0117) → dump 起点对齐 (≈0.013) → permute 布局修正 (≈0.026) → ioDump 逐环节对比 (≈0.53) → ISTFT 语义对齐 + 手写 rfft → OLA writeFrame 竞争 bug 修复 → 0.9877（Redmi）/ 0.9934-0.9947（canoe）。每一步都有明确的 corr 提升，证明根因定位准确。

6per-session 静音方案调研与对比

per-session 静音是实现"用户只听到处理后声音"的关键环节。目标是：在 App 回放分离后音频的同时，将原始目标视频 App 的音频按 audio session 粒度精确静音，而不影响其他 App（如通知、来电）。本章先梳理 Android 音频架构与权限模型的底层知识，再对 7 种候选方案逐一深度分析，最后给出 G+A+E 三层组合方案与实测数据。

6.0 Android 音频架构与 session 机制

6.0.1 Android 音频系统层级

Android 音频系统采用分层架构，从应用层到硬件层共经过 6 个关键阶段：

应用层 App (AudioTrack) → AudioFlinger (混音器) → Audio HAL → DSP / 硬件编解码 → 扬声器 / 耳机
  • App 层：应用通过 AudioTrack 或 MediaPlayer 写入 PCM 数据，每个播放流对应一个 audio session ID。
  • AudioFlinger：Android 音频系统的核心服务，运行在 mediaserver 进程中，负责多路音频流的混音（mixer）、效果器链（effect chain）管理和输出路由。
  • Audio HAL：硬件抽象层，定义了 audio_hw_device 和 audio_stream_out 接口，将 AudioFlinger 的混音结果下发到具体硬件驱动。
  • DSP：数字信号处理器，执行硬件级混音、降噪、均衡等后处理。

6.0.2 什么是 audio session ID

audio session ID 是 Android 音频系统中每个播放流的唯一整数标识，其核心特性如下：

特性说明
唯一性同一时刻每个活跃播放流拥有全局唯一的 session ID，由 AudioFlinger 在创建 Track 时分配
生命周期创建（AudioTrack 初始化 / MediaPlayer prepare）→ 活跃（正在播放）→ 释放（stop/release 后回收）
变化触发条件切换曲目、暂停后恢复（部分 App 会重建 AudioTrack）、切换输出设备（蓝牙↔扬声器）、App 内部重新初始化播放器
作用域session ID 是 AudioEffect 挂载的目标粒度，比 UID 更细——同一 App 的多个播放流可拥有不同 session ID
关键认知 session ID 不是 App 的固定属性，而是播放流级别的动态标识。这意味着静音方案必须具备 session 变化跟踪能力，否则切换视频后静音会失效。

6.0.3 AudioEffect 框架与效果器挂载机制

AudioEffect 是 Android 音频效果框架的基类，DynamicsProcessing、Equalizer、Visualizer 等均为其子类。效果器的挂载机制如下：

  • 挂载目标：效果器通过构造函数的 audioSession 参数挂载到指定 session，或挂载到 0（全局输出 mix）。
  • 链路位置：效果器运行在 AudioFlinger 的 effect chain 中，位于各 Track 混音之前。这意味着挂载到 session 的效果器只处理该 session 的音频，不影响其他 session。
  • 创建流程：App 端 new DynamicsProcessing(priority, sessionId) → Binder 调用 AudioFlinger → AudioFlinger 在对应 PlaybackThread 的 effect chain 中创建 effect module → 返回 effect ID。
  • 启用/禁用：setEnabled(true) 后效果器才真正生效，release() 后从 effect chain 中移除。

6.0.4 为什么 AudioPlaybackCapture 不受 DynamicsProcessing 影响

核心原理 AudioPlaybackCapture 的音频捕获点位于 AudioFlinger 的 RecordThread，它从各 PlaybackThread 的 混音前 Track 数据中拉取原始 PCM 帧——即效果器链（effect chain）上游的音频数据。因此，即使目标 session 上挂载了 -200dB 的 DynamicsProcessing，AudioPlaybackCapture 捕获到的仍然是未经过效果器处理的原始音频。这是本项目"静音但持续捕获"能够成立的根本原因。

6.0.5 Android 权限模型调研

权限保护级别分类

保护级别授予方式典型权限本项目相关
normal 安装时自动授予，无需用户确认 INTERNET, ACCESS_NETWORK_STATE —
dangerous 运行时动态申请，用户弹窗确认 RECORD_AUDIO, READ_EXTERNAL_STORAGE RECORD_AUDIO（AudioPlaybackCapture 需要）

MEDIA_CONTENT_CONTROL 权限

  • 保护级别：signature|privileged
  • 授予条件：应用必须使用平台签名，或安装在 /system/priv-app/ 特权目录下
  • 用途：允许应用控制媒体播放、查询活跃播放配置（getActivePlaybackConfigurations()）
  • 普通 App 行为：Android 12+ 调用 getActivePlaybackConfigurations() 时返回空列表，不抛异常但无数据

DUMP 权限与 shell UID

  • 保护级别：signature|privileged（Android 4.4+ 收紧）
  • adb shell 的特殊性：shell UID（UID=2000）是 Android 系统的特殊调试身份，天然拥有 DUMP 权限，因此 adb shell dumpsys 可以正常执行
  • 普通 App 的限制：App 进程的 UID 是应用自身的 UID（如 u0_a123），不具备 DUMP 权限，Runtime.exec("dumpsys ...") 会被系统拦截
  • logcat 报错：Permission Denial: can't dump ActivityManager from pid=xxx, uid=xxx due to android.permission.DUMP

root / Magisk 在 userdebug 设备上的状态

  • userdebug 镜像：编译时包含 su 二进制，但该 su 仅响应来自 adb shell 的请求（通过 adb root 切换 adbd 为 root 身份），App 进程无法调用
  • Magisk su：通过替换 init 或挂载 Magisk 守护进程，提供任意进程可调用的 su 接口，但需要解锁 Bootloader 并刷入 Magisk
  • canoe 设备状态：userdebug 版本，adb root 可用，但未安装 Magisk，App 内 Runtime.exec("su") 失败

6.1 方案 A：DynamicsProcessing(session, -200dB)

原理深度解析

DynamicsProcessing 是 Android 9 (API 28) 引入的音频效果器，作为 AudioEffect 的子类，提供多频段动态范围控制。其内部信号处理链为：

1
输入增益 (inputGain) — 全局输入增益，范围 -12dB ~ +12dB
2
预均衡 (preEq) — 最多 6 频段参数均衡器，在压缩前调整频谱
3

postEqCount / postEqUse0 / false不启用后均衡

-200dB 的数学含义

增益 dB 值到线性幅度的转换公式为 amplitude = 10^(dB/20)：

  • -200dB → 10^(-200/20) = 10^(-10) = 1×10⁻¹⁰
  • 对于 16-bit PCM（满幅 32767），-200dB 后的幅度约为 32767 × 10⁻¹⁰ ≈ 3.3×10⁻⁶，远低于量化噪声底
  • 对于 float32 PCM（满幅 1.0），-200dB 后的幅度为 10⁻¹⁰，人耳完全不可闻
为什么用 -200 而不是 -∞ DynamicsProcessing 的增益范围下限为 -200dB（而非负无穷），这是 API 的硬约束。-200dB 对应的线性幅度 10⁻¹⁰ 在实际听觉中等同于完全静音，且避免了浮点数下溢（underflow）到 0 后可能引发的除零或 NaN 问题。

6.4 方案 D：dumpsys + su

su 在 userdebug 上的可用性分析

su 类型触发方式App 进程可调canoe 状态
userdebug 内置 su adb root 后 adbd 切 root，adb shell su 可用 否 仅响应 adb shell 的请求 可用（仅限 adb）
Magisk su 任意进程执行 su，Magisk 守护进程授权 是 需 Magisk Manager 授权 未安装

adb root vs Magisk su 的区别

  • adb root：将 adbd 守护进程切换为 root 身份，之后所有 adb shell 命令都以 root 执行。但这只影响通过 adb 发起的命令，不影响设备上已运行的 App 进程。
  • Magisk su：通过 Magisk 守护进程（magiskd）拦截 su 请求，授权后 fork root 子进程执行命令。App 进程可以通过 Runtime.exec("su -c ...") 调用，但需要用户在 Magisk Manager 中授权。
  • userdebug su 的限制：userdebug 镜像中的 /system/xbin/su 源码中检查调用者 UID 是否为 shell（2000）或 root（0），App 的 UID（如 10234）会被拒绝。

验证结果

失败（canoe 上不可行） canoe 为 userdebug 版本但未安装 Magisk，App 内 Runtime.exec("su -c dumpsys media.audio_flinger") 返回 Permission denied。

失败原因

userdebug 镜像的 su 仅允许 adb shell 调用，App 进程 UID 不被信任；Magisk 提供的 su 守护进程未安装。若安装 Magisk，此方案理论可行，但会引入 root 依赖和 SafetyNet 问题，不符合"个人学习最小侵入"的定位。

  • 获取路由列表和 getClientPackageName() 无需特殊权限，普通 App 可直接调用

API 设计层面的限制 MediaRouter2.RouteInfo 的设计目标是路由管理（设备间媒体投射），而非音频流监控。它暴露的最细粒度信息是包名（应用级别），不暴露 audio session ID（播放流级别）。这是 Google 的有意设计——session ID 属于音频系统内部细节，不通过媒体路由 API 对外暴露。因此 MediaRouter2 只能用于"检测哪个 App 在播放"，不能用于"获取该 App 的 session ID"。

定位

作为辅助检测层：自动识别目标 App 包名，配合方案 G 的 session 轮询实现全自动切换。用户无需手动输入目标包名。

6.6 方案 F：AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE

音频焦点机制详解

Android 音频焦点（Audio Focus）机制用于协调多个 App 的音频播放，避免同时发声。焦点类型对比：

焦点类型含义其他播放者行为本项目适用性
AUDIOFOCUS_GAIN 永久获取焦点，预期长时间播放 其他 App 收到 AUDIOFOCUS_LOSS，通常停止播放 不适用 目标 App 停止 → 捕获中断
AUDIOFOCUS_GAIN_TRANSIENT 临时获取焦点，短时间播放（如导航提示） 其他 App 收到 AUDIOFOCUS_LOSS_TRANSIENT，通常暂停 不适用 目标 App 暂停 → 捕获中断
AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK 临时焦点，允许其他 App 降低音量（ducking）继续播放 其他 App 收到 AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK，音量降低但继续 部分适用 目标 App 继续播放但音量降低，原声未完全消除
AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE 临时独占焦点，其他所有播放者暂停 其他 App 收到 AUDIOFOCUS_LOSS_TRANSIENT，强制暂停 不适用 目标 App 暂停 → 捕获中断

目标应用收到 AUDIOFOCUS_LOSS 后的行为

  • 大多数视频 App（如 B站、抖音）在收到 AUDIOFOCUS_LOSS 或 AUDIOFOCUS_LOSS_TRANSIENT 后会暂停播放
  • 部分 App 会调用 AudioTrack.setVolume(0f) 静音但保持播放状态，但这不是标准行为
  • 即使 App 仅暂停音频而视频继续，AudioPlaybackCapture 也会因为没有新的 PCM 帧而停止输出

验证结果

不可行 申请 AUDIOFOCUS_GAIN_TRANSIENT_EXCLUSIVE 后，目标 App 被暂停，AudioPlaybackCapture 捕获到的音频中断，分离处理失去输入源。

失败原因

音频焦点机制的设计哲学是"暂停其他播放者"而非"静音但继续播放"。本项目需要目标 App 持续输出音频以供捕获和分离，音频焦点与此需求根本冲突。即使使用 MAY_DUCK，目标 App 的音量只是降低而非消除，原声仍可闻。

dumpsys 输出的正则解析细节

import re

def parse_dumpsys(output: str, target_uid: int = None, target_pkg: str = None):
    """
    解析 dumpsys media.audio_flinger 输出，提取目标 App 的 session ID。
    匹配策略：优先按 UID 匹配，其次按 client package 匹配。
    """
    sessions = []
    # 匹配 Playback track 行，提取 uid 和 session
    # 典型行: Playback track 0x... (uid=10234, pid=5678, session=42, sample rate=44100, ...)
    track_pattern = re.compile(
        r'Playback track.*?uid=(\d+).*?session=(\d+)',
        re.DOTALL
    )
    # 匹配 client package 行（通常在 track 信息的下一行）
    pkg_pattern = re.compile(r'client package=([\w.]+)')

    lines = output.split('\n')
    current_uid = None
    current_session = None

    for i, line in enumerate(lines):
        track_match = track_pattern.search(line)
        if track_match:
            current_uid = int(track_match.group(1))
            current_session = int(track_match.group(2))
            # 检查后续行是否有 client package
            for j in range(i+1, min(i+5, len(lines))):
                pkg_match = pkg_pattern.search(lines[j])
                if pkg_match:
                    pkg = pkg_match.group(1)
                    if (target_uid and current_uid == target_uid) or \
                       (target_pkg and pkg == target_pkg):
                        sessions.append(current_session)
                    break
            else:
                # 没有 package 信息，按 UID 匹配
                if target_uid and current_uid == target_uid:
                    sessions.append(current_session)

    return sessions  # 返回所有匹配的 session ID（可能有多个播放流）

session 变化检测的逻辑

last_sessions = set()  # 上一次检测到的目标 session 集合

def detect_session_change(current_sessions):
    """检测 session 变化，支持多播放流场景"""
    global last_sessions
    added = current_sessions - last_sessions
    removed = last_sessions - current_sessions

    if added or removed:
        print(f"session change: +{added} -{removed}")
        # 通知 App 更新静音（取当前活跃 session）
        if current_sessions:
            notify_app(list(current_sessions)[0])  # 取第一个活跃 session
        else:
            notify_app(-1)  # 目标 App 停止播放，取消静音
        last_sessions = current_sessions.copy()

7OLA (Overlap-Add) 滑窗方案

OLA（Overlap-Add，重叠相加）是流式音频处理的核心技术，用于将分块推理的输出拼接为连续音频流。本章从信号处理理论出发，深入解析本项目 OLA 系统的架构设计、数据结构、世代计数机制、对齐策略与稳定性保障。

7.0 Overlap-Add 信号处理理论

7.0.1 OLA 基本原理

Overlap-Add 是一种将长信号分帧处理后重建为连续输出的技术。其数学表达为：

OLA 重建公式

y[n] = Σm xm[n - mH] · w[n - mH]

其中：xm 为第 m 帧处理后的输出，H 为 hop size（帧移），w[n] 为分析窗函数，mH 为第 m 帧的起始位置。

物理意义：每帧处理结果乘以窗函数后，按帧移偏移叠加到输出缓冲中。相邻帧的重叠区域通过窗函数的自然衰减实现平滑过渡。

7.0.2 COLA 条件

COLA（Constant OverLap-Add，恒定重叠相加）条件是 OLA 完美重构的充要条件：

COLA 条件

Σm w[n - mH] = 常数（通常为 1），对所有 n 成立

  • hann 窗 + hop=N/2：满足 COLA，重叠区窗值之和恒为 1
  • hann 窗 + hop=N/4：满足 COLA（75% 重叠），重叠区窗值之和恒为 2，需归一化
  • hann 窗 + hop=N/48（本项目）：不满足标准 COLA，重叠帧数高达 48 帧，窗值之和远大于 1，必须使用 WOLA 归一化

7.0.3 为什么本项目 hop=128/N=6144=1/48

MDX-Net 模型的帧结构决定 本项目的 hop=128、N=6144 不是 OLA 理论的最优选择，而是由 MDX-Net 模型的 STFT 参数决定的。模型在训练时使用 hop=128 进行频谱分析，推理时必须使用相同参数才能保证输入分布与训练一致。hop=128 对应 44.1kHz 下约 2.9ms 的时间分辨率，这是音乐源分离模型的常见配置（高时间分辨率有助于瞬态信号分离）。因此 OLA 层必须适配这个极小的 hop，而非反过来选择满足 COLA 的 hop。

7.0.4 WOLA (Weighted OLA) 归一化

由于 hop=N/48 不满足 COLA，直接叠加会导致重叠区能量远高于非重叠区。WOLA 通过维护一个归一化分母来解决此问题：

WOLA 归一化公式

y[n] = Σm xm[n] · w[n] / Σm w²[n]

分子：各帧输出 × hann 窗的累加和
分母：各帧 hann² 窗的累加和（divider）

  • 为什么用 hann² 而非 hann：分析端使用 hann 窗加窗，合成端也使用 hann 窗加权，两帧重叠区的有效窗为 hann × hann = hann²。因此分母应为 hann² 的累加和。
  • 未归一化的后果：重叠区（48 帧叠加）能量约为非重叠区的 48 倍，输出音频出现严重的周期性音量调制（类似镶边效果），波形包络呈梳状滤波特征。
  • 边界处理：在流的起始和结束处，divider 可能小于正常值（未达到稳态重叠数），此时仍按实际累加值归一化，避免边界增益异常。

7.0.5 交叉淡化 (Crossfade)

除了 STFT 级别的 WOLA，本项目在模型输出块级别还设计了交叉淡化机制：

  • 重叠区大小：26368 采样（约 598ms @44.1kHz），即 GEN_SIZE - STEP_SAMPLES = 123904 - 97536
  • 线性交叉淡化：旧窗口输出在重叠区从 1.0 线性衰减到 0.0，新窗口输出从 0.0 线性增长到 1.0，两者相加恒为 1.0
  • 等功率交叉淡化（备选）：使用 cos²/sin² 曲线，重叠区总功率恒定，适用于信号相关性较低的场景
  • 本项目选择：由于相邻窗口的输入数据高度相关（重叠 21.3%），线性交叉淡化已足够平滑，且计算更简单

7.2.1 mdxInput44 的 append-only + front trimming 设计

mdxInput44 采用"尾部追加 + 头部裁剪"的设计，而非传统的环形缓冲区：

  • 为什么不用环形缓冲区：推理需要从缓冲中取连续的 CHUNK_SAMPLES(130048) 字节内存块送入 STFT。环形缓冲区在数据跨越读写指针边界时不连续，需要额外的拷贝操作。append-only 设计保证了取窗时数据始终连续。
  • front trimming 的性能开销：每次取窗后调用 mdxInput44 = mdxInput44.drop(STEP_SAMPLES)，这会创建新数组并拷贝剩余数据。对于 130KB 级别的数组，拷贝耗时约 0.1-0.3ms，远小于推理耗时（110-250ms），可忽略。
  • 内存上限：当推理过慢（如 CPU EP）时，输入缓冲会持续增长。设置上限为 3 × CHUNK_SAMPLES，超过后丢弃最旧的数据（front trimming 更大的步长），防止 OOM。

7.2.2 mdxOlaBuffer / mdxOlaDivider 的环形设计

  • writeFrame 取模寻址：val idx = (offset + i) % mdxOlaBuffer.size，其中 offset = (frame % GEN_SIZE).toInt()。环形设计避免了缓冲的频繁拷贝和内存重分配。
  • 缓冲大小为什么是 GEN_SIZE×2：GEN_SIZE = 123904，缓冲大小 247808。两倍 GEN_SIZE 确保在写入新一帧时，不会覆盖尚未被 AudioTrack 读取的旧数据。AudioTrack 每次读取 STEP_SAMPLES(97536)，读取后该区域可被覆盖，而两倍空间保证了读写指针不会冲突。
  • buffer 与 divider 同步：两个缓冲使用相同的 writeFrame 指针和取模逻辑，确保 buffer[i] 与 divider[i] 始终对应同一输出位置。

7.2.3 mdxOlaEpoch 的原子性要求

  • 多线程访问：mdxOlaEpoch 被推理线程（读取 taskEpoch、比较）和主线程/控制线程（reset 时递增）同时访问。
  • 可见性保障：使用 volatile 或 AtomicLong 确保一个线程的修改对其他线程立即可见，避免 CPU 缓存导致的可见性延迟。
  • 原子性：epoch++ 不是原子操作（读-改-写三步），但 reset 操作通常在单一线程中执行，无需 CAS。若多线程可能同时 reset，则需使用 AtomicLong.incrementAndGet()。

7.3 工作原理

1
采集 — AudioPlaybackCapture 持续写入 mdxInput44（append-only）
2
切窗 — 当 mdxInput44 积累到 CHUNK_SAMPLES(130048) 时，取一窗数据，记录当前 epoch 和 writeFrame
3
推理 — STFT → MDX-Net(ONNX HTP fp32) → ISTFT，异步执行，回调携带 epoch 和 frame
4
世代校验 — 回调时检查 taskEpoch == mdxOlaEpoch，不匹配则丢弃（防止旧流污染）
5
WOLA 叠加 — 将 ISTFT 输出按 hann 窗加权叠加到 mdxOlaBuffer，同步累加 mdxOlaDivider（hann²）
6
输出 — 从 mdxOlaBuffer / mdxOlaDivider 读取 STEP_SAMPLES(97536) 帧，写入 AudioTrack
7
推进 — mdxInput44 头部裁剪 STEP_SAMPLES，writeFrame += STEP_SAMPLES，等待下一窗

7.4 世代计数机制

7.4.1 竞态条件的具体时序

无 epoch 时的污染场景
  1. t0：用户播放视频 A，推理线程提交窗口 W1 的推理任务（携带 frame=0）
  2. t1：用户切换到视频 B，调用 resetOla()，清空 mdxOlaBuffer 和 mdxInput44
  3. t2：推理线程开始处理视频 B 的第一个窗口 W2（携带 frame=0）
  4. t3：W1 的推理结果返回（视频 A 的分离结果），直接写入 mdxOlaBuffer 的 frame=0 位置
  5. t4：W2 的推理结果返回，也写入 frame=0 位置
  6. 结果：视频 A 的陈旧数据与视频 B 的新数据叠加在同一位置，输出爆音、相位错乱、分离质量严重下降

7.4.2 epoch 机制如何解决

t0
提交 W1 推理，taskEpoch = 0
t1
resetOla()：mdxOlaEpoch++ → 1，清空缓冲
t2
提交 W2 推理，taskEpoch = 1
t3
W1 回调：taskEpoch(0) != mdxOlaEpoch(1) → 丢弃
t4
W2 回调：taskEpoch(1) == mdxOlaEpoch(1) → 安全写入

7.4.3 epoch 比较的开销

  • 每次推理回调仅需一次 Long 比较（taskEpoch != mdxOlaEpoch），耗时约 1-2ns
  • 相比推理耗时（110-250ms），开销可忽略不计
  • volatile 读取的内存屏障开销约 10-50ns，仍远小于推理耗时

7.4.4 为什么不用 future / cancellation

推理在 native 层不可中断 MDX-Net 推理通过 ONNX Runtime JNI 调用 native 层执行（QNN HTP EP），推理过程运行在 DSP 或 native 线程中，无法通过 Java 层的 Future.cancel() 中断。即使调用 cancel，native 推理仍会继续执行并返回结果。因此必须采用"提交时记录 epoch，回调时校验 epoch"的乐观并发策略，而非"取消在途任务"的悲观策略。epoch 机制是在不可中断推理约束下的最优解。 
// MDXProcessor.kt — 世代计数防污染
@Volatile
private var mdxOlaEpoch = 0L

fun processWindowAsync(windowData: FloatArray, frame: Long) {
    val taskEpoch = mdxOlaEpoch  // 捕获当前世代（volatile 读）
    val taskFrame = frame
    thread {
        val result = stftInferIstft(windowData)  // 异步推理（不可中断）
        // 回调时校验世代
        if (taskEpoch != mdxOlaEpoch) {  // volatile 读
            Log.w(TAG, "OLA epoch mismatch: task=$taskEpoch current=$mdxOlaEpoch, discard")
            return@thread  // 丢弃过期结果
        }
        // 世代匹配，安全写入 OLA 缓冲
        addToOlaBuffer(result, taskFrame)
    }
}

fun resetOla() {
    mdxOlaEpoch++  // 世代递增，使所有在途结果失效
    mdxOlaBuffer.fill(0f)
    mdxOlaDivider.fill(0f)
    mdxInput44 = FloatArray(0)
    writeFrame = 0L
}

7.6 Idle 检测

7.6.1 Idle 判定阈值的选择

阈值判定逻辑优缺点

7.6.2 源暂停 vs 源静音的区分

  • 源暂停：AudioPlaybackCapture 的 onAudioProgress 回调停止触发，mdxInput44 无新数据写入 → 判定为 Idle → reset OLA 链
  • 源静音：目标 App 播放静音段落（如视频片头黑屏），AudioPlaybackCapture 仍在产生数据（全零 PCM），mdxInput44 持续写入 → 不判定为 Idle → OLA 链继续运行，输出静音
  • 关键区别：Idle 检测基于"是否有数据写入"而非"数据是否为零"，因此源静音不会触发 reset

7.6.3 恢复时的冷启动延迟

源恢复播放后，OLA 链需要重新填充缓冲才能开始输出：

  • 输入缓冲填充：需要积累 CHUNK_SAMPLES(130048) 样本 ≈ 2.95s 才能提交第一窗推理
  • 推理耗时：HTP fp32 推理 0.11-0.25s
  • OLA 输出缓冲填充：第一窗推理结果写入后，AudioTrack 可立即开始播放
  • 总冷启动延迟：≈ 2.95s + 0.25s ≈ 3.2s（从恢复播放到听到分离后音频）
  • 优化方向：可减小 CHUNK_SAMPLES 或使用更小的初始窗（warm-up 帧），但会影响分离质量

private var mdxInput44 = FloatArray(0)  // append-only 输入缓冲，存储捕获的原始 PCM
private var mdxOlaBuffer = FloatArray(GEN_SIZE * 2)   // 环形加权输出缓冲，2倍GEN防覆盖
private var mdxOlaDivider = FloatArray(GEN_SIZE * 2)  // 环形归一化缓冲，累加hann²
@Volatile
private var mdxOlaEpoch = 0L  // 世代计数器，reset时递增，volatile保证多线程可见性
private var writeFrame = 0L   // OLA写入指针（绝对帧位置），取模后映射到环形缓冲索引

// ===== 输入回调：AudioPlaybackCapture 产生新数据 =====
fun onAudioCaptured(pcm: FloatArray) {
    // 尾部追加：新数据拼接到输入缓冲末尾
    mdxInput44 = mdxInput44.append(pcm)
    // 当积累足够一窗数据时，循环取窗（可能一次取多窗）
    while (mdxInput44.size >= CHUNK_SAMPLES) {
        val window = mdxInput44.take(CHUNK_SAMPLES).toFloatArray()
        // 头部裁剪：丢弃已处理的 STEP_SAMPLES，保留剩余供下一窗
        mdxInput44 = mdxInput44.drop(STEP_SAMPLES).toFloatArray()
        // 异步推理：携带当前 writeFrame 和 epoch
        processWindowAsync(window, writeFrame)
        writeFrame += STEP_SAMPLES  // 推进写入指针
    }
}

// ===== 异步推理：STFT → MDX-Net → ISTFT =====
private fun processWindowAsync(window: FloatArray, frame: Long) {
    val taskEpoch = mdxOlaEpoch  // 捕获当前世代（推理开始时的 epoch）
    val taskFrame = frame        // 捕获当前写入位置
    thread {
        // 1. STFT: JNI FFTW3, N=6144, hann, hop=128
        val spec = stft(window)
        // 2. ONNX 推理: MDX-Net, QNN HTP fp32, input (1,4,3072,128)
        val mask = onnxInfer(spec)
        // 3. ISTFT: JNI FFTW3, FFTW_BACKWARD, invN=1/6144, WOLA
        val audio = istft(mask)  // 长度 = GEN_SIZE
        // 4. 世代校验：不匹配说明 reset 已发生，丢弃过期结果
        if (taskEpoch != mdxOlaEpoch) {
            Log.w(TAG, "epoch mismatch: task=$taskEpoch current=$mdxOlaEpoch, discard")
            return@thread
        }
        // 5. 世代匹配，安全写入 OLA 环形缓冲
        addToOla(audio, taskFrame)
        // 6. 触发 AudioTrack 播放
        playFromOla()
    }
}

// ===== WOLA 叠加：将推理结果加权写入环形缓冲 =====
private fun addToOla(audio: FloatArray, frame: Long) {
    // 计算本帧在环形缓冲中的起始偏移
    val offset = (frame % GEN_SIZE).toInt()
    for (i in audio.indices) {
        // 环形寻址：取模防止越界
        val idx = (offset + i) % mdxOlaBuffer.size
        // 分子：输出 × hann 窗加权
        mdxOlaBuffer[idx] += audio[i] * hannWindow[i]
        // 分母：hann² 累加（用于归一化）
        mdxOlaDivider[idx] += hannWindow[i] * hannWindow[i]
    }
}

// ===== 输出：从环形缓冲读取归一化后的音频 =====
private fun playFromOla() {
    // 读取 STEP_SAMPLES 帧，buffer/divider 逐样本相除
    val output = FloatArray(STEP_SAMPLES)
    val readOffset = (readFrame % GEN_SIZE).toInt()
    for (i in 0 until STEP_SAMPLES) {
        val idx = (readOffset + i) % mdxOlaBuffer.size
        // WOLA 归一化：避免除零
        output[i] = if (mdxOlaDivider[idx] > 1e-6f)
            mdxOlaBuffer[idx] / mdxOlaDivider[idx]
        else 0f
    }
    audioTrack.write(output, 0, output.size)
    readFrame += STEP_SAMPLES
}

// ===== Reset：清空所有状态，递增世代 =====
fun resetOla() {
    mdxOlaEpoch++  // 使所有在途推理结果失效
    mdxOlaBuffer.fill(0f)
    mdxOlaDivider.fill(0f)
    mdxInput44 = FloatArray(0)
    writeFrame = 0L
    readFrame = 0L
}

8.3 核心结论

结论 1：STFT/ISTFT 数值对齐完全可行

JNI FFTW3 实现与 PC torch.stft/istft 达到逐位级对齐（corr=1.00000000，max diff=3e-5）。关键在于：periodic hann 窗严格一致、单边谱负频置零（丢弃 Nyquist）、FFTW_BACKWARD 手动 invN 归一化、频域布局 ((ch*2+reim)*3072+k)*128+t 与 ONNX 输入直接映射。移动端频域处理不引入可感知误差。

结论 2：HTP fp32 是移动端推理最优解，低 corr 根因是数据对齐而非 EP 精度

QNN HTP EP 在 fp32 模式下与 PC CPU 逐位一致（corr=1.0），推理 0.11-0.25s/窗，相比 CPU EP 提速 20-60 倍。排查链证明：HTP fp16 (≈0.01) → HTP fp32 未对齐 (≈0.45) → CPU EP 对照 (≈0.0117) 均偏离，根因是 dump 起点不对齐和 permute 轴序错误，而非 EP 本身数值精度。修正后三种 EP 均达 corr=1.0。

结论 3：seg128 是质量、延迟、可行性的最佳平衡点

seg 低于 32 时 U-Net 多级下采样导致 Conv Invalid input shape 不可行；seg64/32 质量分别下降 0.0024/0.0052，有可感知的高频细节损失和音乐噪声。seg128 在 canoe HTP 加速下推理仅 0.11-0.25s/窗，延迟完全被 OLA 缓冲（步进 2.21s）覆盖。静态 shape 导出需同时 ClearField dim_param，避免"假静态"陷阱。

结论 4：全链路质量由推理延迟决定而非推理精度

canoe（HTP）与 Redmi（CPU）初始段（前 2-4 秒）分离质量一致且接近 PC 基准（corr≈1.0），证明模型推理和 STFT/ISTFT 链路本身无差异。整体 corr 差距（0.994 vs 0.828）由 Redmi 4.4-7.4s/窗的推理延迟导致时序漂移——OLA 缓冲无法覆盖延迟，输出逐渐与真实时间轴错位。这是硬件性能限制，非算法缺陷。

结论 5：per-session 静音需 G+A+E 三层组合，单靠 App 内 API 不可行

Android 普通 App 无法获取其他 App 的 audio session ID（MEDIA_CONTENT_CONTROL 和 DUMP 均为系统级权限），7 种候选方案中仅 G（PC adb 辅助脚本）+ A（DynamicsProcessing -200dB）+ E（MediaRouter2 自动检测包名）的三层组合无需 root 且可靠。adb shell 天然有 DUMP 权限，轮询 dumpsys media.audio_flinger 解析 session ID，通过 am broadcast 通知 App 挂载，session 变化 5 秒内自动切换。

结论 6：流式稳定性依赖世代计数、Idle 检测与 dump 对齐三重机制

epoch 世代计数解决异步推理在途结果污染新流的问题（reset 时 epoch++，回调校验不匹配则丢弃）；Idle 检测解决源暂停时 OLA 缓冲陈旧音频残留问题（连续无数据则 reset OLA + flush AudioTrack）；setDumpEnabled(true) 强制 reset OLA 解决验证数据起点不对齐问题。三者共同保障流式处理的可靠性，修复后 canoe 全链 corr 达 0.9934/0.9947。

结论 7：核心目标是 BGM 音量可控降低，output = vocals + bgmGain × accomp

本项目的最终输出不是纯人声或纯伴奏，而是两者的增益混合：output = vocals + bgmGain × accomp。bgmGain 由用户在 0~1 之间调节——0 为纯人声（BGM 完全消除），1 为原声（BGM 不衰减）。这一设计使得项目适用于"看视频时 BGM 盖过人声"的核心场景，用户可根据内容类型和个人偏好在"听清人声"和"保留音乐氛围"之间自由平衡。MDX-Net 的高分离质量（corr 0.9934/0.9947）确保混合后人声清晰、BGM 自然无伪影。
